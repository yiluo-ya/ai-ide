> 透镜 Lens：光标停在哪里，就把「这是什么、从哪来、谁在用它、写得对不对」就地讲清楚，不需要用户先跳走再回来。

## 1. 为什么需要它（用户视角）

读陌生代码时，最大的成本不是「文件打不开」，而是**每读懂一个名字都要付一次往返**。
看到 `resolveRef(...)`，要按 F12 跳过去看签名，再按 Alt+← 跳回来；跳回来之后又忘了刚才那行在干什么。
一次阅读动辄几十次这样的往返，人不是被代码难住，是被**上下文切换**累住。

工具本该消掉这段往返：光标停在名字上，答案就在名字旁边。

当前产品只做到「把代码按语法和归属上了色」，能看出「这是本项目符号、那是外部依赖」，但**说不出它是什么**。
于是用户手里的信息仍然是：颜色告诉了我这里有东西，然后我还得自己去查。

三类用户的具体痛点：

- **读 AI 生成代码的人**：Agent 产出的代码命名陌生、结构陌生，用户往往连「这是个函数还是常量」都要靠上下文猜。
  悬停应当先回答最基础的四个问题：叫什么、是什么、在哪定义、被谁用。
- **做代码评审 / 接手的人**：想知道「我改的这行会不会影响别处」，一眼看到引用处数比跳去引用面板再数更快。
- **带人入门的人**：新人问「这个 `ctx` 是什么」，最省事的回答是指着屏幕说「停上去看」。

透镜的定位因此是**读数器而非跳转器**：它不改变你在哪，只改变你「知道多少」。
它与导航（Navigator）的分工是——悬停负责「值不值得跳」，导航负责「跳过去」。

L1/L2 已经给了「哪里重要」的视觉信号，但缺了最后一步语义。
补上悬停，等于把已有的索引成果第一次以**人话**暴露到编辑器表面，是当前投入产出比最高的一块。

- L3 五项都标 ✗，因为全仓没有任何悬停提供者与悬停端点；`DefRecord.detail`（声明首行）虽已存在，但只服务于大纲与符号搜索，从未在光标处呈现。
- L5 与 L3d 有交叠：短期的类型展示只能来自签名文本本身，不引入推断；这一点决定了它在边界里被严格限定。
- L8 的折叠是 Monaco 默认能力，项目未显式关闭，也没有定制折叠策略（如「按注释块折叠」）。

## 3. 关键交互形态

### 3.1 悬停卡片（L3a–L3e + L4 + L5 + L7 的统一载体）

默认：鼠标停在符号上约 300 ms 浮出；移开即收；不使用键盘焦点，不打断输入（只读态无输入）。
字段自上而下按「身份 → 位置 → 契约 → 解释 → 影响」排列，一眼能扫完。

```
          ┌─ 悬停卡片 ──────────────────────────────────────────┐
          │  fetchUser                      [method]           │  ← L3a 名字 + 种类
          │  class UserService                                  │  ← L3b 所属容器
          │  backend/src/user.ts:42                             │  ← L3c 定义位置（可点）
          │  ───────────────────────────────────────────────    │
          │  @cache                                             │  ← L7 装饰器（若有）
          │  async fetchUser(id: string): Promise<User>         │  ← L3d 声明首行签名
          │                                                     │
          │  按 id 取用户；命中缓存时直接返回。                  │  ← L4a docstring / 注释
          │                                                     │
          │  引用 7 处                                          │  ← L3e 影响面（可点开）
          └─────────────────────────────────────────────────────┘
  光标 ───┘
```

收敛规则（决定「没信息时不弹垃圾」）：

```
光标处没有可解释的符号（空白、关键字、字符串字面量本身）
        → 不弹卡片，保持安静

符号是外部依赖（print / os.path / 第三方包）
        → 卡片只显示「外部依赖 · 不在索引内」，不给跳转、不给引用数

能解析但签名缺失（如赋值给变量的匿名函数）
        → 只显示 名字 / 种类 / 位置 / 引用数，不留空行占位

索引尚未完成
        → 收起卡片并在需要时提示「索引中」，而不是给出「无定义」的错误结论

同名多定义且无法区分
        → 全部列出（文件:行），由用户自己认，不替用户猜一个
```

### 3.2 解析失败态：把「不知道」也说清楚（L3 的边界能力）

失败态是透镜可信度的关键：宁可说不知道，也不能给错答案。
所有失败都收敛成一句可行动的话，不暴露内部 reason 枚举。

```
场景                        卡片内容
──────────────────────────────────────────────────────────
外部依赖        │ print        [外部依赖]
                │ 标准库 / 第三方包，不在项目索引内
──────────────────────────────────────────────────────────
需要类型推断    │ user.getName() 中的 getName
                │ 无法确定 user 的类型，暂不能定位定义
                │ （可跳转到 user 本身）
──────────────────────────────────────────────────────────
索引未完成      │ 索引进行中，符号信息稍后可查
──────────────────────────────────────────────────────────
未解析的普通名  │ 未找到定义：可能是运行时注入或未索引文件
```

### 3.3 常量与字面量溯源（L6）

悬停对象从「名字」扩展到「值」：这是透镜唯一一次回答「这个值是什么」而不是「这个名字是什么」。

```
  const TIMEOUT_MS = 30;                    let retry = 3;
                     ↑                                     ↑
             光标停在 30                        光标停在 3

  ┌─ 值 30 ────────────────────────────┐   ┌─ 值 3 ────────────────────────────┐
  │ 绑定到常量 TIMEOUT_MS               │   │ 绑定到变量 retry                  │
  │ 定义：config/limits.ts:12           │   │ 定义：net/client.ts:88            │
  │                                    │   │                                   │
  │ 同值出现 5 处                       │   │ 同一变量的其他引用 4 处            │
  └────────────────────────────────────┘   └───────────────────────────────────┘
```

收敛规则：
- 字面量未被任何定义绑定（如函数调用里的 `60`）→ 只说明「字面量，无关联定义」，不强行编造来源。
- 字符串若同时是导入路径 / 配置键，优先显示它作为「引用」的角色，并给出跳转。

### 3.4 整文件密度概览条（L10）

> 命名区分：本条是**单个文件内部的行密度**（每 20 行区间的代码 / 注释 / 空白占比），
> 与 01 地图 M11.4 的「符号密度（每文件定义数）」**同名不同义**——落地后文案与实现一律称「行密度条」。
> 实现口径：段内注释占比 ≥ 0.45 且不低于代码占比 → 注释堆；空白占比 ≥ 0.45 且不低于代码占比 → 空壳；
> 其余算代码密。文档设想的「空壳 = 声明多、实现少」缺一项声明占比，实现用空白占比近似（已在代码注释注明）。

只读态没有滚动条以外的「整文件感」。密度条把整文件压缩成一条可扫的带子，回答「哪里值得读」。

```
  编辑器右缘（与 minimap 并列，可收起）：

  ┌ 文件密度 ──────────────────────────────┐
  │ ▓▓▓▓░░▓▓▓▓▓▓▓░░░▓▓▓▓░░▓▓▓▓▓▓▓▓▓▓▓▓▓ │  ← 每格 = 一段行区间的密度
  │  代码密    注释堆   空壳    长函数       │
  └────────────────────────────────────────┘
       ↑ 悬停某格：该段起止行 + 主要符号名，可点击跳过去

  颜色口径（只表达「是什么」）：
    代码密  = 语句/符号密度高
    注释堆  = 连续注释占比高
    空壳    = 声明多、实现少（大量接口/占位）
```

## 4. 与其它五个主题的关系

- **与 01 地图 Map**：透镜看单点，地图看全局，二者共用同一份索引事实。
  密度概览条（L10）是「单文件版地图」；地图的热点文件（谁被引用最多）与透镜的引用处数（这个符号被用多少次）是同一把尺子的两种粒度。
  读代码的典型路径是「先用地图挑文件，再用透镜读懂文件里的每一行」。
- **与 03 导航 Navigator**：透镜负责「值不值得跳」，导航负责「跳过去」。
  悬停卡片里的定义位置与引用处数本身就是入口：点位置等于跳定义，点引用数等于看引用列表。
  这样用户不必先跳走也能决定要不要跳，减少无效跳转——这是导航失败的兜底（跳转失败的解释可以由透镜承担）。
- **与 04 向导 Guide**：悬停是最小粒度的「解释」。
  当向导将来做「解释这一段」「这个文件在干嘛」时，L3/L4 提供的事实层是它的输入；透镜先保证「单点事实可信」，向导才有资格谈「成段的叙述」。
  反过来，向导若引入 LLM，透镜仍应保持「只陈述索引里确定的事实」，不把猜测混进悬停。
- **与 05 信使 Share**：悬停卡片里的「签名 + 定义位置」天然是可复制、可粘贴给同事或 agent 的最小上下文单元。
  复制位置、复制带出处的签名，是分享行为里最低成本的一档；透镜顺便提供了「分享什么」的内容。
- **与 06 底座 Platform**：透镜的准确率完全等于索引的准确率，是索引质量最直观的对外窗口。
  「不做类型推断」这一底座限制直接决定 L5 的天花板；注释提取（L4）、字面量索引（L6）、装饰器（L7）是否需要新增索引能力，是底座要不要扩面的决策点。
  只读定位也在这里体现：悬停只展示、不修改，卡片不含任何写回动作。

**结论**：透镜的「识色」已完整，「释义」为零。
L3 所需的全部事实（名字、种类、容器、位置、签名、引用）当前**都已在索引里**，缺口在「没有把它们送到光标处」。
L4/L6/L7 需要扩展索引采集面，L5 在「不做推断」的约束下只能展示已有注解文本，L10 需要新的行级统计。

## 6. 边界（明确不做）

- **不做类型推断**：延续项目定位，悬停不引入 LSP / TS 语言服务去猜 `obj.method()` 的类型。悬停只陈述索引里确定的事实；类型信息仅来自源码中已写的注解或签名文本，推断不出来就说不知道。
- **不做编辑型能力**：补全、签名帮助、参数提示、快速修复、重命名一律不做——它们服务于「写代码」，与只读阅读器定位冲突，且会立刻把产品拖进与 IDE 的正面竞争。
- **不显示诊断**：不出现波浪线、错误面板、类型错误提示。只读阅读器不承担「代码写得对不对」的裁判职能（当前 TS/JS 诊断已被显式关闭）。
- **不索引依赖包内部**：悬停命中 node_modules / site-packages 等外部符号时，只标注「外部依赖」，不跳转、不显示其源码，也不内置第三方文档站。
- **不把悬停变成助手**：不引入 LLM 做「即时解释」「总结这段」。悬停的回答必须短、确定、可核对；成段叙述属于向导（Guide）的范畴。
- **卡片不承载操作**：除跳转 / 复制这类只读动作外，卡片里不放编辑、执行、批注等任何会改变状态的入口。
- **不做全语言齐头并进**：注释 / 装饰器 / 字面量这些需要按语言解析的能力，允许先在覆盖度高的语言上可用，未覆盖语言明确显示「暂无此信息」，不用兜底文本假装有。

## 7. 演进阶段

透镜的价值随「事实密度」递增，因此按「先确定事实、后解释性内容、最后统计概览」推进。

**阶段一：把已有事实送到光标处（L3a–L3e）**
用一个悬停卡片承载索引里已经存在的东西：名字、种类、容器、定义位置、声明首行签名、引用处数。
同步做失败态收敛：外部依赖、需要推断、索引中、未解析，各自给一句人话。
这是投入最小、覆盖率最高的一步——不新增索引能力，只新增一次呈现。

**阶段二：引用数可点、定义位置可跳（L3c/L3e 深化）**
让卡片的两个数字/位置成为入口：点位置即跳定义，点引用数即打开引用列表。
这一步开始与导航（Navigator）的常驻引用面板合流，避免两套「看引用」的交互并存。

**阶段三：注释与文档（L4a/L4b）**
按语言补齐 docstring 与紧邻注释的提取，卡片才真正具备「解释性」。
需要按语言分别取舍：函数级注释、行尾注释、块注释的归属规则各不相同，宁可少不要错。

**阶段四：类型与装饰器（L5、L7）**
从签名文本中切出参数/返回类型并独立成行，展示定义上的装饰器/注解清单。
明确不走推断，只做「源码里写了就展示，没写就不显示」。

**阶段五：值溯源与密度概览（L6、L10）**
字面量溯源需要新的索引采集面，放在事实层稳定之后。
密度概览条作为「单文件地图」，与主题 01 的整体规划一起设计，避免两边对「密度」的定义不一致。

L1/L2/L8/L9 为既有能力，不作为演进项；本文档只要求后续演进不破坏它们（例如悬停不覆盖语义着色，密度条不挤占 minimap）。

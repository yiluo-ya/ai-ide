> 向导是产品的「教练」：它不回答「这段代码是什么」，而回答「我该先看什么、按什么顺序看、看懂了没有、刚才读到哪了」——把一次漫无目的的翻文件，变成一条走得完的路线，并且这条路线上留下我的痕迹。

## 1. 为什么需要它（用户视角）

这个产品的前提是：用户拿到的代码**不是自己写的**（尤其由 AI 生成），目标不是「找到某个能跑通的地方改一行」，而是「弄明白它在干什么」。

在这样的场景里，真正的困难不是「代码看不见」——文件就在左侧树里，点得开、能搜、能跳。真正的困难是**没有入口、没有顺序、没有终点**：

- **打开一个陌生仓库，第一分钟是空转的。** 文件树上几百个文件，哪个是入口？哪个是核心？README 可能没有，或者写的是安装步骤而不是架构。用户能做的只有随机点开一个文件，从中间某一行开始读，读到一半发现自己根本不知道这个函数被谁调用。当前产品在这一分钟里给的是一张写着快捷键的欢迎页（`frontend/src/App.tsx:195-213`）——它回答了「怎么操作」，没回答「从哪开始」。
- **读完没有顺序感。** F12 跳定义能让你从 A 跳到 B，但它是**你驱动的**：你得先猜到哪里值得跳。读了 40 个文件之后，回头看自己走过的是一条锯齿状的线，没有建立任何整体印象。用户需要的是「先读被依赖的底层，再读依赖它的上层」这类可以照做的顺序，而不是一次次碰运气的跳转。
- **不知道自己读到哪了。** 关掉标签页、第二天回来，一切归零。当前的前进后退栈只在内存里（`frontend/src/state.ts:219-249`），切项目就清空，刷新就消失。对「花了三个晚上读一个大项目」的用法来说，这是致命的：每次回来都要重新找位置，读过的文件看不出读过，没读过的文件看不出该不该读。
- **读懂了，但说不出来。** 读到关键处会有一句「哦，原来这里是为了处理 X」——如果不写下来，这句话两天后一定忘。当前的阅读是纯输入，没有任何给自己留话的地方。
- **代码在动，而我的认知停在三天前。** 这是本产品最独特的场景：代码很可能是 agent 刚生成、还在被 agent 继续改的。用户合上阅读器吃饭，回来时代码库已经变了 40 行——而当前只有「文件被改了，我帮你重载一下」这个级别的反应（`frontend/src/state.ts:147-151`）。用户需要的是「**与上次阅读相比，变了什么**」，这直接决定了他要重读哪些部分、哪些笔记已经过期。
- **可视化缺失导致只能线性读。** 调用流、数据流在脑子里拼不出一张图。跳转是逐点的，而理解是整体的。

一句话：地图（主题 01）回答「这个项目长什么样」，向导回答「**我接下来该做什么**」。前者是看板，后者是路线加脚印。没有向导，前面的所有能力（跳转、搜索、大纲、着色）都只是「更快的翻页工具」，用户依然要靠自己组织这次阅读。

## 3. 关键交互形态

### 3.1 首屏引导页（「从这里开始」）

项目已打开、但还没选文件时，编辑区不再是空白欢迎页，而是这个项目的总览与起点清单。这是向导的主入口，也是用户一天中的第一个画面。

```
+---------------------------------------------------------------------------------+
| 代码阅读器 | [项目: xchen-core v] | 打开本机目录 | 已索引 42 个文件 | ?          |
+--------------------+------------------------------------------------------------+
| 文件树              |  从这里开始 · xchen-core                                   |
|  src/               |  --------------------------------------------------------  |
|    indexer/         |  这个项目：42 个文件 · Python 31 / TypeScript 11 · 无 README |
|    api/             |  未提交改动：4 个文件（3 天前看过）                          |
|  tests/             |                                                            |
|  docs/              |  入口候选（点击直接开始）                                    |
|                     |   [1] src/main.py           程序启动入口          →          |
|                     |   [2] src/api/routes.ts     对外接口定义          →          |
|                     |   [3] src/indexer/store.ts  核心数据结构          →          |
|                     |                                                            |
|                     |  推荐路线                                                   |
|                     |   依赖序 · 12 步 · 预计 40 分钟            [开始] [换一条]   |
|                     |   config.py → model.py → store.py → routes.ts → …          |
|                     |                                                            |
|                     |  继续阅读                                                   |
|                     |   src/indexer/store.ts:120（3 天前，已有 5 条笔记）  [继续]  |
+--------------------+------------------------------------------------------------+
| src/main.py                                                        Ln 1, Col 1 |
+---------------------------------------------------------------------------------+
```

要点：首屏的每一块都可点击直达，不是一个静态说明页；「换一条」让用户在依赖序 / 入口向下 / 热度序 / 新鲜度序之间切换。

### 3.2 阅读路线的呈现（侧栏卡片 + 行进控制）

路线不是一张图，而是一张**可执行的清单**：每一步是一个文件，带序号、状态和「为什么是它」。它常驻侧栏，用户可以随时离开路线自由探索，再从原处继续。

```
+--- 路线：依赖序（12 步） -------------------------- [收起] ---+
|  已完成 4 / 12                 [换一条]  [重排]  [存为我的路线] |
|                                                               |
|   v 1. src/config.py          配置读取     已读               |
|   v 2. src/indexer/model.ts   数据结构     已读               |
|   v 3. src/indexer/parser.ts  AST 封装     已读               |
|   v 4. src/indexer/store.ts   索引主体     已读（5 条笔记）    |
|   > 5. src/api/routes.ts      对外接口     在读  <- 你在这里   |
|     6. src/registry.ts        项目注册表   待读               |
|     7. src/watcher.ts         文件监听     待读               |
|     …                                                         |
|                                                               |
|  为什么是这个顺序：6 依赖 4；2 与 3 被 4 依赖                  |
+---------------------------------------------------------------+
|  [上一步]  [下一步]  [标记已读]  [加入待读]                     |
+---------------------------------------------------------------+
```

要点：状态由系统给默认值（打开过、停留时长），但**任何一步都能手动改**——用户对「读懂了没有」的判断权优先于系统的推断。当前文件读完时，编辑器底部给一条「下一步：src/registry.ts →」的提示条，把行进动作放进阅读动线里。

### 3.3 笔记附着在代码上

笔记挂在**行**上（也支持文件级），以行槽图标 + 悬浮卡的形式出现，不修改源文件一个字节。右侧笔记面板是所有笔记的汇总视图。

```
+--------------------+------------------------------------------------------+
| 文件树              |  1  def handle(req):                                  |
|    src/            |  2      order = parse(req)            (*)  <- 行槽图标 |
|      api/          |  3      if not order.valid:      +----------------+   |
|      indexer/      |  4          raise BadOrder(      | 本行笔记 (2)   |   |
|      registry.ts   |  5      stock = check(req)       | > 为什么这里不 |   |
|                    |  6      return save(order)       |   校验库存？   |   |
|                    |                                  |                |   |
|                    |                                  | + 写一条笔记   |   |
|                    |                                  +----------------+   |
+--------------------+------------------------------------------------------+
| 笔记 12 条 · [全部] [当前文件] [导出 Markdown]   文件级笔记：老代码，别照抄 |
+---------------------------------------------------------------------------+
```

要点：笔记必须**跨会话存在**，否则这个能力没有意义（当前产品全仓没有任何本地存储，见第 5 节）。笔记是「我给自己留的话」，不是协作评论：没有他人、没有回复、没有已解决状态。

### 3.4 变更感知（「自上次阅读以来」）

这是本产品与普通阅读器最不一样的一块：代码在动。用户回来时先看到变化清单，决定重读范围，而不是从头找。

```
+--- 自上次阅读以来（2026-09-29 → 今天）--------------------------------+
|  变了 4 个文件 · 新增 38 行 · 删除 12 行                              |
|                                                                      |
|   M  src/service/order.py     +34 -10   改动较大   [看差异] [重新读]   |
|   A  src/store/cache.py       +120      新文件     [看差异] [开始读]   |
|   M  src/api/routes.ts        +4  -2    [看差异] [已读，跳过]          |
|   D  src/legacy/old.py                  [看差异]                      |
|                                                                      |
|  提示：你在这 2 个文件上有 5 条笔记，其中 2 条所在的行已被改动          |
|  [只看我笔记过期的文件]                                               |
+----------------------------------------------------------------------+
```

要点：变更清单的价值不只是「知道变了」，而是与**阅读状态和笔记联动**——「你标注过的地方被改了」是这条路线里最高优先级的信号，它告诉用户「你的认知需要更新了」。

## 4. 与其它五个主题的关系

- **01 地图 Map（上游，供给全景原料）**：地图产出入口候选、热点文件、依赖分层、目录职责；向导把这些原料**变成顺序和动作**。分界：地图是「看板」，回答「这个项目长什么样」；向导是「路线 + 脚印」，回答「接下来做什么、做过了什么」。本主题的 G2（路径）、G9（流视图）强依赖地图的依赖/调用网络；没有地图，G2 只能退化成按文件名和热度排序。
- **02 透镜 Lens（分工，不问同一个问题）**：透镜是「自动、即时、零成本」的单点信息（悬停出签名、颜色分档、docstring）；向导的 G5「解释这段」是「用户主动发起、成本更高、输出更长」的讲解。分界很清楚：**能在一秒内不花钱答出来的，归透镜；需要理解上下文、需要用户专门请求的，归向导。** 同理 G6.1 与透镜的「文件头注释 / 签名展示」不重复：透镜展示已有信息，G6.1 汇总是系统生成的判断。
- **03 导航 Navigator（互补，一个管移动，一个管方向）**：导航让用户「能到任何地方」（跳定义、查引用、搜索），向导决定「值得去哪、去过哪醒」。G3 与 N20 书签、N21 最近打开、N22 位置记忆高度相邻，实现上应当共享同一份本地记录，但语义不同：书签是用户手动钉的点，进度是系统对「读没读懂」的推断，最近是原始流水账。
- **05 信使 Share（下游，把向导的产物带出去）**：路线、进度、笔记、摘要都是「带得走」的内容——路线可以编成深链序列发给同事，笔记导出 Markdown，G4.4 的交付形态由信使承接。向导负责「产生」，信使负责「输出」。
- **06 底座 Platform（硬依赖，决定向导能不能存在）**：向导是六个主题里**唯一需要写状态**的主题（进度、笔记、阅读快照、路线），因此它把两件事变成前提：①本地持久化（存哪、怎么跨会话、怎么跟项目 id 绑）；②隐私承诺（这些数据全在本机、不上传）。G5/G6 是否引入 LLM 也会直接改变底座边界（是否留模型侧、用户代码会不会离开本机）；G7 git 集成还要求底座给出「如何访问本机 git 仓库」的通道与权限边界。
- **与本主题重叠的两个已有能力**：Monaco 的深链/postMessage（主题 05 已做）让向导的每一步天然可分享、可被宿主驱动；`state.ts` 的 history 栈（已有）是「最近读过什么」的雏形，但它是内存态、切项目即清空，不能直接当进度用。

## 5. 现状证据（只列事实）

1. **首屏是静态欢迎页**。未打开文件时编辑器区渲染固定文案：标题、一句操作提示和 4 条快捷键说明，没有任何与当前项目相关的内容（`frontend/src/App.tsx:195-213`）。打开项目后也不会自动打开文件，切换项目只拉文件树与索引状态（`frontend/src/state.ts:123-156`）。
2. **全仓没有本地持久化**。`localStorage` / `sessionStorage` / `indexedDB` 在整个仓库（前端、后端、shared）零命中——没有任何进度、笔记、书签的存储位置。前端状态是 zustand 内存态（`frontend/src/state.ts:77-97`），刷新即丢。
3. **只有内存态的历史栈**。`history` / `historyIndex` 存在（`frontend/src/state.ts:94-95`，`HISTORY_LIMIT = 300` 见 `frontend/src/state.ts:62`），由 `openFileAt` 压栈、`goBack` / `goForward` 消费（`frontend/src/state.ts:219-249`）；切换项目时被清空（`frontend/src/state.ts:134-135`），且不落盘，只服务 Alt+←/→。
4. **没有 git**。后端依赖只有 Hono、chokidar、tree-sitter 系列（`backend/package.json`），前端无 git 库；源码中 `git` 的唯一命中是把 `.git` 放进忽略目录（`backend/src/indexer/store.ts:20`）。没有任何 git 命令调用、diff、blame 或历史读取。
5. **变更感知只有「重载」级别**。后端用 chokidar 监听项目目录，300ms 防抖后合并增量更新索引（`backend/src/watcher.ts:25-46`），并通过 SSE 推送 `file-changed` / `file-deleted`（README 的 API 表列有 `/api/projects/:id/events`）；前端收到后只做三件事：重载文件树、重载当前打开的文件、刷新语义着色（`frontend/src/state.ts:147-151`）。没有任何变更清单、差异或摘要呈现。
6. **mtime 原料在，但没走出索引层**。`EntryInfo` 含 `mtimeMs`（`backend/src/indexer/store.ts:40-44`），扫描时写入（`backend/src/indexer/store.ts:135`），`FileIndex` 也带 `mtimeMs`（`backend/src/indexer/model.ts:86`）；但对前端暴露的 `FileNode` 只有 `count` / `lang` / `size`（`shared/types.ts:72-83`），没有时间字段；API 路由里也没有输出时间的地方（`backend/src/api/routes.ts`）。
7. **语言分布字段只有类型声明**。`langStats: Record<string, number>` 只出现在 `ProjectFiles` 接口里（`backend/src/indexer/model.ts:117`），全仓未见填充与输出（单文件全局检索仅此一处命中）。
8. **没有 LLM**。后端做的是 tree-sitter 静态分析（解析、定义/引用提取、模块说明符解析），全部本地完成；依赖清单里没有模型 SDK，源码中无模型调用（`backend/package.json`，全仓检索 `openai` / `anthropic` 等零命中于源码）。
9. **可视化只有清单，没有图**。前端渲染层是 Monaco 只读编辑器（`frontend/src/Editor.tsx`）、文件树、大纲与搜索面板（`frontend/src/SidePanel.tsx`）、搜索弹层（`frontend/src/QuickOpen.tsx`），没有图/树/流视图组件。
10. **可用的原料确实存在**。索引里有文件树，以及跨文件的名字级映射 `defsByName` / `refsByName` / `importsByName`（`backend/src/indexer/store.ts:65-67`），它们是 G2（热度/依赖序）、G9（调用/反向调用）、G6.1（这个文件被谁用）的直接原料。
11. **入口相关的引导目前只有一处**：顶栏的「打开本机目录」按钮与提示（`frontend/src/TopBar.tsx:55-80`），它解决「怎么加载一个项目」，不解决「加载之后从哪开始」。

## 6. 边界（明确不做）

| 不做 | 理由 |
|---|---|
| 完整 git 客户端（提交、暂存、切分支、合并、推送） | 只读定位是差异化。git 集成只取「读懂」需要的读数：状态、diff、blame、历史，任何写操作一律不做 |
| 笔记 / 进度写回源文件 | 本产品承诺不改动磁盘内容，写回会在别人的仓库里留下脏文件。笔记只能存在本产品自己的数据里（存哪见第 8 节） |
| 用笔记当协作评论（指派、回复、@人、已解决） | 那是代码评审工具的活。这里的笔记默认只有一个读者：写笔记的人自己 |
| 多人协作、账号、云端同步 | 本机工具，隐私即卖点；一旦要云，向导的数据（笔记、快照）也会离开本机，与只读/不上传承诺冲突 |
| 笔记（G4.1–G4.4）/「存成笔记」（G5.4） | 2026-10-03 用户决定移除：只存本机、没有分发通道；行级备注与讨论交给 PR/MR（恢复补丁见 `docs/patches/reading-notes.md`）。与之一并摘除的还有书签（N20）与批注（S10） |
| 已读 / 待读（G3.1 / G3.2 / G3.5） | 2026-10-08 用户决定移除：不需要判断是否已读，也不要待读清单。随之删除「打开即已读」的自动推断、已读进度与「标记已读 / 全标已读」、文件树与编辑器右键与搜索命中行尾的「加入待读」入口；阅读路线（G2）与「继续阅读」（G3.3/G3.4）保留 |
| 运行、测试、覆盖率、性能剖析驱动的「进度」 | 向导判断「读懂了没有」只能基于阅读行为与静态结构，不引入运行期证据 |
| 自研类型推断 / 数据流精确求解 | G9.3 的数据流只做「基于已有定义与引用关系的简化视图」，不承诺编译器级的准确度；精确能力若需要，应接现成的 LSP 而不是自己造 |
| 全仓库自动摘要（把整个项目喂给模型生成一份总述） | 成本高、时效差（代码一改就过期）、且涉及把大量源码送出本机。摘要只做文件/模块粒度、按需触发 |
| AI 自动改代码 / 自动生成补丁 | 超出只读阅读器的定位，与本产品「帮人理解」的目标正交 |
| 把阅读路径做成硬编码的「最佳实践」 | 路线只是建议，用户可以随时离开、重排、替换；产品不做「你必须按这个顺序读」的权威判断 |

## 7. 演进阶段

形态级切分，与总体版本切分（见 `FR/FR-0003-fr-2.md` 的 V2 / V4 / V5）对齐；每一阶段都以「用户能完成一件以前做不到的事」为完成标志。

| 阶段 | 主题 | 范围 | 完成标志（用户视角） |
|---|---|---|---|
| **W0 现状** | 白纸 | 只有欢迎页 + 快捷键清单 | 打开陌生项目后，第一分钟仍然靠自己乱点 |
| **W1 起步（首屏 + 路线）** | 「我知道从哪开始了」 | G1.1–G1.4、G2.1–G2.5、G6.1 | 打开项目后，我看到入口候选和一条可执行的路线，点「开始」就能一路读下去，不用自己找第一个文件 |
| **W2 有记忆（位置 + 笔记）** | 「我回到上次的地方了」 | G3.3–G3.4、G4.1–G4.4 | 关掉浏览器再回来，位置与笔记都还在；我能导出笔记（2026-10-08 起 已读 / 待读 已移除） |
| **W3 变更有感（对齐 agent 节奏）** | 「代码动了我立刻知道」 | G8.1–G8.4、G7.1–G7.4 | agent 改完代码，我打开阅读器先看到变更清单，并知道哪些笔记所在的行被改了 |
| **W4 会解释（须先拍板 LLM）** | 「我不用自己啃了」 | G5.1–G5.4、G6.2–G6.4、G7.5 | 选中一段能拿到讲解与文件摘要，且能存成笔记；不引入模型时，这一步退化为 G5.2 的结构性解释 |
| **W5 看得见（流视图）** | 「整条链路在眼前」 | G9.1–G9.4 | 从一个入口能看到调用链，从一个函数能看到谁在用它；数据流给简化视图而非编译器级精度 |

排序理由：W1 不依赖持久化，是这个主题里**最快能被用户感知**的一步；W2 一旦引入持久化，W3 的变更感知才有对照物（「自上次阅读以来」需要一个「上次」）；W4 的分水岭是 LLM 决策，不能与前三阶段绑死；W5 依赖地图与导航的可视化承载，放在最后。

## 8. 待确认问题

> **状态更新（2026-10-02）**：以下 6 个问题已全部拍板并落地，答案与依据见 `04-decisions.md`（Q1–Q6），落地结果见 `04-guide-plan.md` §9。
> 本清单保留为「问题从哪来」的溯源记录，不再是待决事项。一句话结论：**纯静态不引入模型**（Q1-A）、**已读 = 打开过 + 可手动覆盖**（Q2-A）、**数据只存本机 localStorage 并可导出**（Q3-A）、**只读 git 命令 + 无 git 时降级为快照对比**（Q4-A）、**默认依赖序**（Q5）、**不服务团队场景**（Q6-否）。

1. **G5/G6 是否引入 LLM？** 三选一：A. 纯静态——「解释这段」和摘要只输出基于符号/引用/调用关系的结构化信息，代码永不出本机，主题定位为「纯静态向导」；B. 引入——接模型做自然语言解释与摘要，主题升级为「AI 助手」，同时要接受代码片段离开本机、以及模型成本；C. 双轨——静态版本永远可用作默认与兜底，AI 版本按需开启（开关放用户手里）。**这条不拍板，W4 无法开始，底座是否要留模型侧也不定。**
2. **进度里的「已读」怎么判定？** A. 打开过就算；B. 打开并停留超过若干秒（或滚动到底）才算；C. 完全手动标记，系统不猜。可以选 A/B 作默认 + 允许手动覆盖，请确认默认档位。
3. **笔记与进度存在哪里？** A. 只存浏览器本地（`localStorage` / IndexedDB），清缓存即丢，但零侵入；B. 存后端数据目录（与项目 id 绑定），换浏览器还在，但要注意与「不改动被打开目录」的边界不冲突（数据放本产品自己的目录）；C. 存到被打开项目内的一个隐藏目录（如 `.reader-notes/`），可以随 git 一起提交给同事 —— 但这与「只读、不写磁盘」的承诺直接冲突，需要明确豁免。请选一个。
4. **G7 git 集成走哪条通道？** A. 调用本机 `git` 命令（能力全，但要求用户环境装了 git，且要处理路径/权限）；B. 只读解析仓库内的 `.git` 目录（不依赖外部命令，但能力有限、边界脆弱）；C. 先不做 git，W3 只做「与上次阅读快照对比」的变更感知。三种的交付成本与能力差别很大，请指定。
5. **阅读路径的默认排序按什么？** 依赖序（先底层后上层）/ 入口向下序（跟随程序执行流）/ 热度序（被引用最多优先）/ 新鲜序（最近改动优先）。请指定一个默认，其余作为「换一条」的备选；这直接决定 G2.1–G2.4 谁先做。
6. **向导是否需要服务「同事 / 团队」这个场景？** 是——那么笔记、路线、摘要需要考虑分享与导出（与主题 05 强耦合），并可能需要首次使用引导与更友好的空状态；否——一切以单人本机效率为最优先，分享能力只做「复制深链」这一档。请回答是或否。

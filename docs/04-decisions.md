## Q0 交付范围

- **问题**：04 共 40 项能力（G1.1–G9.4），一次交付规模极大；做到哪一步？
- **选项**：A 只做 W1 起步（首屏 + 路线）｜B 五阶段全量｜C 只出清单不写码。
- **决策**：**B，五阶段全量，不做裁剪。** 每阶段独立可验收，验收不过不进下一阶段。
- **依据**：04 的 W1–W5 已经是文档作者给出的自然切分（`04-guide.md:208-217`），且每阶段的排序理由要求「W2 的持久化先于 W3 的变更感知」（没有「上次」就没有「自上次阅读以来」）。裁剪会破坏这条依赖链。
- **代价**：G9 的图视图与 G4 的笔记是两处最重的交互实现；G7 的 git 扩展受本机是否装 git 制约（已定降级路径，见 Q4）。

## Q1 是否引入 LLM（04 §8-1）

- **问题**：G5.1「解释这段」与 G6.3「自然语言摘要」是否接模型？
- **选项**：A 纯静态｜B 引入模型｜C 双轨（静态兜底 + AI 按需）。
- **决策**：**A 纯静态。**
- **依据**：
  1. 本产品的差异化和前提是**只读 + 本机 + 不上传**（`04-guide.md:173`、`04-guide.md:197`）。引入模型意味着用户没写的代码（很可能是私有仓库）离开本机，这与「隐私即卖点」直接冲突，且需要用户自己承担成本与合规判断。
  2. 后端当前无任何模型 SDK、进程内无网络调用（`backend/package.json:13-28`），引入即新增一条外部依赖与密钥管理链路，属 06 底座量级的决策，不该由 04 顺带决定。
  3. 04 自己给了退化路径：W4 的完成标志写明「不引入模型时，这一步退化为 G5.2 的结构性解释」（`04-guide.md:214`）。而 G5.2 所需的定义 / 引用 / 调用 / 大纲索引**已经全部落地**（03 的 N1–N17），产出足以回答「这段调用了谁、引用了哪些本项目定义、属于哪个类的哪个方法」。
- **落地口径**（必须写进界面）：
  - G5.1「解释这段」= G5.2 的结构性解释（符号清单 + 调用清单 + 出处链接 + 覆盖率），不出现任何「AI 生成」字样。
  - G6.3「自然语言摘要」→ **模板化摘要句**：后端用已有的结构化字段拼一句确定性的中文（如「导出 3 个符号（2 类 1 函数），依赖 4 个模块，被 7 处引用，其中测试 2 处」），界面标注「结构性摘要 · 未使用模型」。
  - **不留**「以后接模型的开关」占位：没有实现的东西不写进界面。

## Q2 「已读」怎么判定（04 §8-2）

> **已作废（2026-10-08 用户要求清除「已读 / 待读」）**：不再判断「是否已读」，本节决策不再适用；如下保留作为历史记录。

- **选项**：A 打开过就算｜B 打开并停留超时/滚到底才算｜C 全手动。
- **决策**：**A 作默认 + 允许手动覆盖**（原文允许的组合档）。
- **依据**：
  - 系统的职责是**记事实**（打开过），不是**猜理解**（读懂没读懂）。B 的「停留时长」在本产品里尤其不可靠：用户完全可能打开一个文件、扫一眼发现读不懂就走；而「滚动到底」对 3000 行的文件等于永远不达标。
  - C 太苛刻：用户要的是「回来看见哪些读过」，手动标全部文件是纯负担。
  - 04 明确「用户对『读懂了没有』的判断权优先于系统的推断」（`04-guide.md:123`），与「A + 手动覆盖」一致。
- **落地要点**：`openFileAt` 成功后写已读标记；文件树右键「标记已读 / 标记未读」（**复用 01 已落地的 `wcr.map-marks` 的 `read` 子集**，不新建一份存储）；路线卡片上的「标记已读」写同一份。

## Q3 笔记与进度存在哪里（04 §8-3）

- **选项**：A 浏览器本地｜B 后端数据目录（与项目 id 绑定）｜C 项目内隐藏目录。
- **决策**：**A**，并补「**显式导出 / 导入 JSON**」。
- **依据**：
  - **C 直接排除**：与「不改动被打开目录一个字节」的承诺冲突（`04-guide.md:195`），不能为了便利破例。
  - **B 排除（本次）**：会把向导数据与后端进程、`data/` 目录、项目注册表绑在一起，等于让「在浏览器里读代码」这件事依赖一个服务端存储；且 03 已经把书签 / 位置记忆 / 搜索历史统一放在 `localStorage`（`README.md:209-210`），两套存储会让「哪些数据在哪儿」变成用户要记的事。**数据落在同一层，口径才单一。**
  - **A 的已知代价**（如实写进界面帮助文案）：清缓存即丢、不跨设备。补偿手段就是导出 JSON（衔接 05 信使的交付形态）。
- **落地要点**：沿用 03 已确立的 key 命名 `wcr:<域>:<projectId>`，全部读写真值包 `try/catch`（隐私模式 / 配额异常静默降级）；新增域：`routes`（当前路线与自定义顺序）、`notes`（笔记）、`readsnapshot`（阅读快照）、`queue`（待读）。

## Q4 G7 git 集成走哪条通道（04 §8-4）

- **选项**：A 调用本机 `git` 命令｜B 只读解析 `.git`｜C 不做 git，只用阅读快照。
- **决策**：**A**，并保留 C 作为**降级路径**（无 git 时不报错、自动走快照对比）。
- **依据**：
  - 01 已经落地了只读 git 通道（`backend/src/indexer/timeline.ts:110-150`，`rev-parse` / `status` / `log` 三命令 + 4000ms 超时 + 失败静默降级），`git()` 是通用 args 透传包装（`timeline.ts:89-100`），扩展 `diff` / `blame` / `show` 的成本是两个函数，不是一条新链路。
  - B（自己解析 `.git`）能力残缺且脆弱：packfile、delta 编码、各种 ref 形态都要自己实现，做出来还不敢保证准 —— 违反「绝不伪造数据」。
  - C 不足以覆盖 G7.3 blame 与 G7.5 历史版本（快照里没有作者与历史）。
- **落地纪律**（延续 01 的注释纪律）：
  - 只用 `git log` / `status` / `rev-parse` / `diff` / `blame` / `show` 六个**只读**命令；**任何写操作（commit / add / checkout / stash）一律不做**。
  - 一律走 `execFile('git', ['-C', root, ...args])` 数组传参，不经 shell，不接受任何拼接的字符串命令（避免注入）。
  - 每次调用带 `timeout`，失败返回 `null` 并降级；界面在降级时如实注明「未检测到 git，使用阅读快照对比」。

## Q5 默认阅读路线（04 §8-5）

- **选项**：依赖序 / 入口向下序 / 热度序 / 新鲜度序。
- **决策**：**依赖序为默认**；其余三条作为「换一条」备选；W1 四条路线**一次全做**。
- **依据**：
  - 本产品的目标是「弄明白一个不是自己写的项目在干什么」，**最需要被解释的是结构**。依赖序（先被依赖的底层，再依赖它的上层）直接消除「读到一半发现自己不知道被谁调用」这一最痛的现状（`04-guide.md:12`），且它是四个选项里唯一**不需要用户先有假设**的路线 —— 入口向下序要求先认出入口、热度序要求先接受「被引用多=重要」、新鲜度序只对「agent 刚生成」的场景成立。
  - 四条路线的原料（`importsByName` / `refsByName` / `mtimeMs` / `looksLikeEntry`）都已存在（`backend/src/indexer/store.ts:68-76`、`insight.ts:964-969`），分开做只会让「换一条」按钮在 W1 里点不动 —— 那不是「起步」，是半成品。

## Q6 是否服务团队场景（04 §8-6）

- **决策**：**否。**
- **依据**：一旦承认团队场景，就要考虑笔记的分享语义（谁能看、怎么同步）、路线的一致性、首次使用引导与更友好的空状态 —— 这些都会把产品推向「轻量协作工具」，而它已经明确不做协作评论（`04-guide.md:196`）与账号云端同步。**单人本机效率优先**，分享只保留三档零成本形式：复制深链（03 已有）、导出笔记 Markdown、导出笔记/书签/路线 JSON。

## Q7–Q20：梳理落地路径时新暴露的问题

### Q7 首屏与 01 地图的关系 —— **同一页面，向导是叠加层**

- **决策**：**不新建首屏。** 未选文件时的主区仍渲染 01 的 `Overview`（已落地），向导在其上追加四段：「从这里开始（入口候选）」「推荐路线」「继续阅读」「自上次阅读以来」。
- **依据**：01 §1.1 与 04 §3.1 描述的是同一个画面（打开项目后的第一眼）。两份「首屏」会让用户第一眼就要选择看哪个，且 01 的地图已经包含语言分布、入口候选与热点 —— 04 需要的「规模 / 语言分布 / 有哪些入口」正是它的产出（`Overview.tsx:284-426`）。**加区块，不加页面。**

### Q8 进度的分母 —— **两级口径，都要标注**

> **已作废（2026-10-08 清除「已读」）**：已读进度整体移除，本节决策不再适用；如下保留作为历史记录。

- **决策**：路线内进度 `已完成 4 / 12 步`（主）＋ 项目级 `已读 12 / 40 个源码文件`（辅）。
- **分母定义**：索引中的**源码文件**（`project.files` 的键），**排除**测试文件（`isTestFile`）、文档与配置（`isDocOrConfig`）。
- **依据**：把测试与配置算进分母会让进度永远推不到 100%（用户不会去读测试夹具），反而失去意义；但分母口径必须写在界面上，否则「12/40」这个数字来路不明。

### Q9 笔记与行的绑定 —— **anchor 文本快照 + 三层兜底**

- **决策**：每条行级笔记存 `{file, line, col, anchor}`，`anchor` = 该行去首尾空白后截前 120 字符。
- **恢复顺序**：① 行号命中且 anchor 匹配 → 直接用；② anchor 不匹配 → 在该行 ±30 行范围内搜同一 anchor；③ 仍找不到 → 进「待归位」列表（顶部提示条 + 笔记面板分组），**不静默丢弃、不猜位置**。
- **依据**：代码在动是本产品的前提（`04-guide.md:15`），笔记若只绑行号，agent 每改一次上方代码就会把所有笔记错位；而错位的笔记比没有笔记更糟 —— 它会让人相信一句贴错位置的判断。

### Q10 阅读快照 —— **每项目一份，防抖写**

- **决策**：`wcr:readsnapshot:<projectId>` = `{at, files: {[path]: {mtimeMs, size, lines}}, noteLocs: {[noteId]: {file, line, col}}}`；写时机：`openFileAt` 成功后防抖 2s、切项目时立刻写。
- **依据**：G8.2「自上次阅读以来」需要「上次」这个对照物（`04-guide.md:217` 的排序理由），而 01 已落的 `timeline` 只能给「相对今天/3 天/7 天」，答不了「相对我上次阅读」。`lines` 字段是为 Q18 的行数增减兜底准备的。

### Q11 路线生成放哪一层 —— **后端**

- **决策**：新增 `GET /api/projects/:id/routes`，一次返回四条路线（`dep` / `entry` / `hot` / `fresh`），每条含 `steps[{file, reason, order}]` 与 `total`。前端只做呈现与状态。
- **依据**：与 03 的「后端 `reason` 是唯一事实源」同源 —— 依赖序需要全项目 import 图去环、拓扑分层，前端手上只有文件树；若前端自己算，就出现了第二份「为什么是这个顺序」的判定，必然漂移。

### Q12 待读队列与书签的关系 —— **独立存储，并列展示**

> **已作废（2026-10-08 用户要求清除「待读」）**：待读队列已移除，本节决策不再适用；如下保留作为历史记录。

- **决策**：待读队列独立 key `wcr:queue:<projectId>`（条目 `{file, line, col, note?, at}`），不加进书签结构；UI 上两者并列在向导面板与侧栏 marks tab。
- **依据**：语义不同 —— 书签是「我确认这里重要」，待读是「我还没看、别忘」。合并成一个结构后，「什么时候该从列表里移除」就出现了两种规则，UI 必然要说清「这条是哪种」。**拆成两个 list，各有一条移除规则，反而更简单。**
- **入口**：文件树右键「加入待读」、搜索命中行尾 `+`、编辑器右键「把当前位置加入待读」。

### Q13 向导面板挂在哪 —— **侧栏第 8 个 tab**

> **2026-10-08**：清除「已读 / 待读」后，面板内只剩「路线」与「继续阅读」两段（面板本身自 2026-10-03 起已不在界面上挂入口）。

- **决策**：`PanelTab` 增加 `guide`，内含「路线 / 进度 / 待读 / 笔记」四段；快捷键 `Ctrl/Cmd+8`（延续 03 的 `Ctrl/Cmd+1..7`）。
- **依据**：这些内容都是「常驻、可随时离开再回来」的，符合侧栏 tab 的既有形态；做成浮层会与全屏搜索、依赖图两个浮层抢同一块屏幕。

### Q14 G9 流视图的承载 —— **复用 d3-force + SVG**

- **决策**：新建 `frontend/src/FlowView.tsx`（浮层，与 `.graph-overlay` 同机制），复用 01 依赖图的 d3-force 布局与手写 SVG 交互（`GraphView.tsx:523-611` 的 wheel 缩放 / pointer 平移）。
- **依据**：依赖图已经证明这套技术栈在本项目跑得通（无 canvas、无 d3-zoom，自己算 viewBox）；换技术栈会新增依赖与一套新的交互习惯。**需要把 `GraphView` 里的布局纯函数（`layoutGraph` / `nodeRadius` / `nodeFill` / `nodeTitle` / `labelVisible`）显式导出复用，不复制一份。**

### Q15 数据流的精度边界 —— **名字级近似，界面标注**

- **决策**：G9.3 只做「基于已有定义与引用关系的简化视图」：从调用点的实参文本出发，做**名字级**匹配（实参标识符名 ↔ 定义参数名 / 返回标识符名 ↔ 接收变量名），命中即连一条边并标注来源。
- **依据**：04 §6 已明确不做自研类型推断（`04-guide.md:199`）。名字级匹配是**可以解释**的启发式（「因为两边都叫 order」），而「看起来像类型推断但会错」的边会让人误信整张图。界面固定标注「名字级近似 · 不做类型推断」。

### Q16 摘要由谁生成 —— **后端，模板化句子**

- **决策**：`GET /api/projects/:id/file-summary?file=` 返回 `{file, lang, lines, kind, exports[], imports[], inbound{total, top[], tests}, outbound[], longestFunction?, doc?, revision, sentence}`；`sentence` 由后端用这些字段拼装（确定性，不调模型）。目录级摘要直接复用 01 的 `dirDuties`（`insight.ts:600-692`），不新增算法。
- **依据**：三种原料（大纲 / imports / 引用计数）都在后端，前端拼要发 3 个请求；`revision` 用 `indexVersion` 让前端能做 G6.4 的时效标记。

### Q17 笔记的交互形态 —— **行槽图标 + 自建 React 浮层**

- **决策**：行槽（`linesDecorationsClassName`）渲染 `wcr-note-gutter` 图标（已有笔记高亮）；点击通过 `editor.onMouseDown` 的 `GUTTER_LINE_DECORATIONS` 目标打开编辑浮层；浮层是自建 React 组件（与 `Notice.tsx` / 密度条同风格），定位用 `editor.getScrolledVisiblePosition`。
- **依据**：Monaco 的 contentWidget 需要自己管 DOM 与 lifecycle，本项目已有 `Notice` 这套「自建浮层 + 编辑器坐标」的成熟做法（03 已用），复用成本最低。**注意**：现有 `agent-lines` 与语义着色各占一个装饰池（`Editor.tsx:31-39`），笔记必须使用**第三个独立装饰池**，避免互相清掉。

### Q18 变更的增删行数从哪来 —— **优先 git，其次快照**

- **决策**：git 仓库走 `git diff --numstat HEAD`（含未跟踪文件另算，用行数统计）；非 git 仓库用快照的 `lines` 与当前行数对比，**只报净增减**，界面标注「无 git，仅行数对比」。
- **依据**：04 §3.4 的形态里 `+34 -10` 是可读性关键（`04-guide.md:155`），但伪造这个数字比不给更糟。降级路径必须诚实。

### Q19 历史版本怎么看 —— **只读快照，不落盘**

- **决策**：`GET /api/projects/:id/git/show?rev=&path=` → 正文；前端在 Monaco 里用 `wcr-history://<rev>/<path>` scheme 开一个只读 model 展示，标签条上标「历史版本」。
- **依据**：只读承诺要求不把历史版本写进被读目录（也不写任何临时文件），Monaco model 是内存对象，天然满足。

### Q20 阶段验收 —— **三关，与 03 同口径**

- **决策**：每阶段必须过 `npm run typecheck`、`npm test`、`npm run test:ui`；新增能力的 UI 用例进 `tests/ui/`（现有 19 条，追加向导相关用例）。
- **依据**：04 的能力几乎全是交互行为（「这条路线点开始能不能一路走下去」「关掉浏览器回来还在不在」），单测覆盖不到；03 已经搭好 Playwright 回归的骨架（`tests/ui/run.mjs` + `navigator.mjs`），**复用而不是另起一套**。

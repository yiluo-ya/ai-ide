> 信使 Share：把我读到的那个位置、那段代码、那份理解带走并交出去 —— 交给人，也交给 agent。

## 1. 为什么需要它（用户视角）

一个只读阅读器最容易死在这里：**理解只发生在我的屏幕上**。我花了二十分钟把一个 AI 生成的项目读通了，关掉标签页，一切归零；明天要跟同事说「就是 `auth.py` 第 42 行那个地方」，得手动抄一遍路径和行号；想让 agent 别再用 grep 猜我的代码，却没有任何通道把「我已经建好的索引」借给它。

用户真正会说的三句话：

- 「**我读到的这个点，怎么一句话发出去**」——同事、未来的我、或者 agent，拿到之后能直接落到同一行，而不是靠描述去猜。
- 「**这段代码我要贴到聊天窗里讨论**」——贴出去的片段必须自带出处（哪个文件、哪几行），否则三天后没人知道它从哪来。
- 「**我读懂了，怎么把这份理解交出去**」——不是交一份源码，而是交一份「按这个顺序看这几处」的东西；同时，agent 想查代码时，应该能查索引，而不是 grep。

再往上提一层，信使也是「这个工具能不能给别人用」的问题：目标形态是 share，意味着同事拿到就能跑、自己一条命令起得来；也意味着它可以被宿主（如 xchen 的项目列表）直接嵌进去，宿主点一下项目就进阅读器，阅读器反过来告诉宿主「用户正在读哪」。

所以信使的定位是两个词：**带得走**（位置、片段、理解、整份交付物）与**接得上**（接宿主、接 agent）。

## 3. 关键交互形态

### 形态 A：宿主与阅读器的握手（现状单向，目标双向）

```
现状：只有宿主 → 阅读器，阅读器不回话
宿主（xchen 项目列表）                          阅读器（iframe）
   │  GET  /api/projects/lookup?root=…             │
   │──────────────────────────────────────────────▶│  查是否已注册
   │  POST /api/projects { root }                   │
   │──────────────────────────────────────────────▶│  注册并开始索引
   │  iframe src=/?project=..&file=..&line=..       │
   │──────────────────────────────────────────────▶│  直接定位
   │  postMessage({ type:'wcr:open', root, file … })│
   │──────────────────────────────────────────────▶│  跳到位置
   │                                                │
   │   （没有任何回音：宿主不知道用户读到哪、索引好没好）

目标：宿主与阅读器互相知道对方状态
宿主                                            阅读器
   │  GET /api/health  ────────────────────────────▶│  探活
   │  postMessage  wcr:open  ──────────────────────▶│  跳转指令
   │◀────────────  wcr:ready  { projectId, status } │  就绪 + 索引进度
   │◀────────────  wcr:state  { file, line, sel? }  │  换文件 / 移动 / 选中
   │  postMessage  wcr:dispose ────────────────────▶│  宿主收起面板
   │◀────────────  wcr:bye                          │  已释放资源
```

回发粒度按「换文件必发、行号跟随、选区后置」推进：先在换文件时回发，行号作为附带信息；选区与选中符号的粒度是 S7b 的内容，噪声更大，单独评估。

### 形态 B：agent 从「猜代码」变成「查代码」

```
Agent（Claude / 其它宿主）                    代码阅读器后端
   │  可用工具：index_project / find_symbol /        │
   │            goto_definition / find_references /   │
   │            file_outline / search_text            │
   │                                                  │
   │  ① 我要改登录，先确认入口在哪                     │
   │     find_symbol("login") ───────────────────────▶│
   │◀──── [ src/auth.py:42  func login, … ] ──────────│
   │  ② 谁在用它                                       │
   │     find_references(file=src/auth.py, line=42) ─▶│
   │◀──── [ src/routes.py:88, tests/test_auth.py:12 ] │
   │  ③ 拿上下文再动手                                  │
   │     read_file(file=src/auth.py, 30..60) ────────▶│
   │◀──── 30~60 行正文 ───────────────────────────────│
   │  ④ 写代码（这一步不经过阅读器）                    │
```

关键点：agent 手里拿到的是**符号级**答案（文件 + 行列 + 符号名 + reason），而不是 grep 出来的字符串匹配；「解析不出」也照实说，不编造。

### 形态 C：iframe 全生命周期

```
宿主                                       阅读器
 │ ① 拉起：iframe src=/?project=…             │
 │──────────────────────────────────────────▶│  加载前端、打开项目
 │ ② 探活：GET /api/health                   │
 │──────────────────────────────────────────▶│  { ok: true }
 │   未起 → 宿主提示「阅读器未启动」或自动拉起   │
 │ ③ 就绪：wcr:ready { projectId, status }    │
 │◀──────────────────────────────────────────│
 │ ④ 使用：wcr:open  ↔  wcr:state             │
 │◀─────────────────────────────────────────▶│
 │ ⑤ 退出：wcr:dispose / 直接卸载 iframe      │
 │──────────────────────────────────────────▶│  释放资源：关 SSE、停 watcher、释放内存索引（注册表条目保留）
 │ ⑥ 确认：wcr:bye（可选）                    │
 │◀──────────────────────────────────────────│
```

①⑤ 是生命周期，②③ 是状态可见性，④ 是使用期；只有 ④ 的「宿主 → 阅读器」方向已经存在。

## 4. 与其它五个主题的关系

- **01 地图 Map**：地图回答「这项目长什么样、从哪开始」，信使负责把地图上的坐标变成能贴出去的东西（入口文件的链接、热点清单的报告）。地图给信使内容，信使给地图出口。
- **02 透镜 Lens**：着色与解释留在屏幕上就带不走。导出的截图 / Markdown 必须保留透镜的结论（哪是本项目符号、哪是外部依赖），否则导出等于退化成纯文本。
- **03 导航 Navigator**：信使是导航的延续。单点深链只是「一个位置」，而「我走过的那条路」（历史、引用列表、调用层级）才是完整的交接内容；导航能力越强，信使能交出去的东西越厚。
- **04 向导 Guide**：向导产出的阅读路径天然是给同事的交接单，信使负责把它从内存状态变成一份文件（报告、清单、带顺序的链接集）。
- **06 底座 Platform**：信使能不能把东西送出去，先由底座决定 —— 一键启动、单机分发、端口与单实例、索引持久化、隐私承诺。S5 与 S9 的边界几乎全部由底座划定，信使只是把它们组织成用户可见的形态。

## 6. 边界（明确不做）

- **不做编辑、运行、编译、调试、重构**：只读是差异化定位；信使只搬运「位置与文本」，不搬运「改动」。
- **不做云端托管、账号、权限与在线协同服务**：不提供「发个链接给外部的人打开看」的 SaaS 形态。要给人，就给人「能自己跑起来的那一份」；隐私即卖点。
- **不把被读代码复制到临时目录**：现在就是目录直读，这是既有的形态决定；若要做 S5b 的「打包带走」，必须单独立形态决策，而不是顺手打破它。
- **不做代码片段的执行或沙箱**：导出的片段是给人读的，不是给人跑的。
- **批注不写回源码文件**：S10 的批注是对代码的评论，不能污染被读项目（具体存哪见第 8 节）。
- **agent 工具只读**：不对 agent 开放改文件、执行命令、跑测试的能力，只开放「查」。
- **不做整仓公开分享页**：导出与交付以「文件 + 阅读器本体」为单位，不做把整仓发布到公网的形态。

## 7. 演进阶段

形态分四步走，每步都有可验证的完成判据；阶段之间不互相阻塞，但顺序决定了「先能用」的是什么。

**阶段 A：带得走一条线索（S2、S3）**

- 形态：在编辑器里选中一段或把光标停在一处，一键得到「相对路径 : 行 : 列」与「带出处行号的代码片段」，贴进聊天窗口即可用。
- 完成判据：同事 / agent 拿到粘贴内容后，能直接定位到同一文件同一行，而不需要问「哪个文件」。

**阶段 B：带得走一份东西（S4、S5）**

- 形态：把当前文件、当前搜索结果或整份索引摘要导出成不依赖阅读器也能看的形态；同事在另一台机器上能读到同一份代码。
- 完成判据：导出的 Markdown 报告在纯文本环境里仍然可读、位置可点；「同事拿到就能打开同一份代码」的路径被明确选成第 8 节问题 1 中的某一项并跑通一次。
- 前置：S5 走哪条路必须先拍板，否则导出做得再多也只是自娱自乐。

**阶段 C：接得上宿主（S7、S9）**

- 形态：xchen 项目列表里嵌入阅读器，点项目就进、收起面板就干净退出；宿主面板能显示「用户正在读哪」。
- 完成判据：宿主一处改动即可拿到阅读器状态；宿主收起面板后没有残留的 watcher / SSE / 后台进程。

**阶段 D：接得上 agent（S8）**

- 形态：把已有的索引与解析能力包装成 agent 可调用的工具（协议待定，见第 8 节问题 2），agent 在真实任务里能拿它替代「grep + 猜测」。
- 完成判据：一次真实的代码修改任务中，agent 通过工具而不是文本搜索确定了「定义在哪、谁在调用」；对解析不出的位置，工具如实返回「未解析」而不是给错误答案。

**延伸：能讨论（S10）**

- 形态：在代码行上留批注、形成可回复的线程，并能随导出物一起交付。
- 前置：批注存哪必须先定；在此之前不做。

## 9. 落地对照与结果

> 阶段 A→D 加 S10 全部落地，与能力清单逐项对照见 §2（除 S5b 均已 ✅）。

### 9.1 结论

信使从「只能单点深链、只有宿主单向指令」变成**端到端可交付**：

- **带得走**：位置 / 片段 / 符号三种粒度都能一键复制，且**自带出处**（`path:line:col`）；
- **带得走一份东西**：Markdown 报告（文件 / 搜索 / 概览）与截图都保留了「哪是本项目符号、哪是外部依赖」，脱离阅读器仍然可读；
- **接得上宿主**：握手从单向变双向（`ready` / `state` / `bye`），宿主收起面板时资源真的释放（且可核对）；
- **接得上 agent**：8 个只读 HTTP 工具上线，agent 可以查符号 / 定义 / 引用而不靠 grep 猜；解析不出如实返回 `unresolved`。

### 9.4 边界与遗留

- **S5b 未做**（决策 C）：跨机器仍是「你自己跑一份」；要打包源码需单独立形态决策，不顺手打破「目录直读」。
  （2026-10-02 复核：用户确认**先不做**，维持「留作后续阶段」——这是本主题唯一未落地项，其余 S1–S10 均已实现并验证。）
- **S8 只做 HTTP**（决策 B）：换宿主（Claude Desktop 等）不可直接复用，但查询语义一致，以后包 MCP 层即可。
- **截图与打印的范围**：都只能覆盖当前渲染出来的视口（不是整文件分页），界面上以「当前可见范围」「打印 / 存 PDF」如实称呼。
- **批注只在本机**：换机器 / 换浏览器就没了 —— 这是「不碰被读项目」这一前提的直接代价，靠「导出批注 Markdown」缓解。
- **信任边界默认收紧**：宿主需在 iframe URL 上带 `?hostOrigin=<宿主源>`（或登记过）；被忽略的来源只在控制台留说明，不打断阅读。

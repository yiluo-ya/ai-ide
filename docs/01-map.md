> 地图 Map：打开一个陌生项目，先不看任何一行代码，就回答「这项目长什么样、有几块、哪几处最重要、从哪开始读」。

## 1. 为什么需要它（用户视角）

这个产品最有价值的时刻，是用户拿到一份**自己没写过**的代码：AI agent 刚产出的整个仓库、同事交接的项目、自己三个月前开的坑。
这时他面对的第一个问题不是「这个函数怎么实现的」，而是更前面的一层：

- 这项目有多大、用了哪些语言、大概分几块？
- 入口在哪？主流程从哪个文件开始？
- 这么多文件里，哪几个是骨架、哪几个是边角？
- 最近改动集中在哪？哪些是新写的、哪些是 agent 刚生成的？

**当前的答案是：没有答案。** 打开项目后，用户看到的是一个静态欢迎页——一堆快捷键说明，和这个项目本身毫无关系（`frontend/src/App.tsx:195-213`）。
唯一可用的信息是左侧文件树，而文件树只回答「有这些文件」，不回答「该看哪个」。
于是用户的阅读方式退化成随机点开：点开一个文件，扫两眼，不知道它在整体里的位置，关掉，再点下一个。
这不是阅读，是碰运气。

**成本在哪。** 一个 200 文件的项目里，真正构成骨架的可能只有 8–15 个：入口、核心数据结构、被到处引用的工具模块。
用户要靠试错把它们找出来，成本 = 打开次数 × 每次「这是不是我要找的」的判断成本。
更糟的是这个成本**每次重开项目都要重付一遍**，因为工具不记忆、不总结、不给全景。
地图要做的就是把这件从「探索」降级成「选择」：一眼看到候选，点进去即可。

**三类具体时机。**

- **第一次接触（陌生仓库）**：需要「三分钟建立心理地图」——先知道有几块、每块叫什么、块之间怎么连，再决定从入口读还是从热点读。
- **回到自己的旧项目**：需要「我上次改到哪了、哪些是新的」。时间维度比结构维度更重要，此时「最近改动」就是导航图。
- **验收 AI 产出**：agent 一次生成十几个文件，用户需要一个「本轮它都产出了什么、这些文件挂在哪、互相怎么引」的清单，而不是逐个文件去猜哪些是新的。

**为什么现在必须做。** 三点：

1. 它是**当前最大的空白**。导航（Navigator）已做到一半，透镜（Lens）有语义着色打底，而地图几乎是零——首屏除了欢迎页什么都没有。
2. 它是**其它主题的共同前置**。向导（Guide）要「带人按路径读」，可是没有地图就没有「有哪些地方可读」；信使（Share）要「把价值带走」，其中最值得带走的就是这张地图；透镜与导航的入口也都站在地图上。
3. 它的**原料已经攒好了**。文件清单、大小、修改时间、目录结构、跨文件引用表、项目内模块解析（import 到文件的落地）都已建好，只是没有一个界面消费它们。
   这意味着地图的第一版不需要新增索引能力，只需要把已有事实**算出来并画出来**——投入产出比在整个产品里属于最高的一档。

**地图回答四个问题**，也对应下面能力清单的四组：它是什么（M1、M4）、从哪开始（M2、M3）、结构如何（M5、M6、M7、M8、M11）、时间与来源（M9、M10）。

## 2. 能力清单

现状三态：✅ 已有 · ◐ 半成品 · ✗ 完全没有。本主题目前**没有一项端到端可用**，◐ 表示「原料已在索引里、或符号级能力可近似回答」，但仍缺按项目/按文件的聚合与呈现。

| M10.3 | 会话/批次视图（本轮产出清单） | 一轮对话产出的文件应当成组呈现，可批量过一遍 | ✗ | 侧栏总览区块 | M10.1 + M9.2 |
| M10.4 | 阅读确认标记（已读 / 已认可） | 十几个新文件，读过的要能划掉，否则会重复读 | ✗ | 文件树徽标 + 总览进度 | 本地状态存储（当前无） |
| M11.1 | 规模指标（行数、文件大小） | 快速判断哪些文件是「巨物」，读之前先有心理准备 | ◐ | 总览列表列 | `entries.size` 与文件索引里的 size |
| M11.2 | 结构复杂度（圈复杂度、嵌套深度、函数长度） | 圈复杂度是「这段代码读起来要绕几个弯」的最直接代理量 | ✗ | 总览列表列 / 排序 | 索引期已有的 AST 遍历能力 |
| M11.3 | 依赖复杂度（每文件出度/入度） | 「依赖了 40 个模块的文件」和「没人依赖的文件」是完全不同的阅读对象 | ◐ | 总览列表列 | import 表可按文件聚合；入度需 M5.1 |
| M11.4 | 符号密度（每文件定义数/导出数） | 判断文件是「一堆小工具」还是「一个大类」 | ◐ | 总览列表列 | 定义表 + 已索引文件表 |

> 命名区分：本项说的是**跨文件的符号密度**（一个文件里有多少个定义）。
> 02 透镜的「整文件密度概览条」是**单个文件内部的行密度**（每 20 行的代码 / 注释 / 空白占比），
> 两者同名不同义，实现与文案上一律分别称「符号密度」「行密度条」。

现状口径说明：

- M1.3、M9.1、M11.1、M11.3、M11.4 标 ◐，是因为**数据已在索引里**（文件大小、修改时间、每文件 import 与定义），只是没有按项目聚合的说法、也没有任何界面展示。它们的地图版本几乎不需要新采集，只需要聚合与呈现。
- M3.1 标 ◐ 的特殊性：拿单个符号按 Shift+F12 已经能看引用（符号级），但「按文件被引用次数排序的 Top N」不存在——需要把名字级引用聚合到文件级、并排除同文件自引用与噪声。
- M6.1 标 ◐ 同理：符号级反向查询可用，文件/module 级不可用。
- M2.1/M2.2 是 ✗，不是 ◐：全仓没有任何入口识别逻辑，连文件名启发都没有。
- M7、M8、M10 是整块空白，连近似能力都没有。

```
    ▓ routes.ts           ▓▓  昨天       │       [ ] agent 产出      │
  ? tmp/scratch.ts        ·   从未被引用 │       [ ] 孤立文件        │
                                         └──────────────────────────┘

徽标含义（同一套，贯穿全产品）：
▣ = agent 产出的文件        ▓ = 改动热力（越亮越新）      ? = 孤立/无人引用
```

这个形态直接服务「验收 AI 产出」与「回到旧项目」两个高频时机：勾上「agent 产出」后，文件树立刻变成一份本轮交付清单。

## 4. 与其它五个主题的关系

- **与 02 透镜 Lens**：两者共用同一份索引事实，粒度相反——地图是「多文件一张图」，透镜是「一个名字一张卡」。
  地图上的每个条目（文件、目录、模块）若要被解释「这是什么」，正是透镜的职责；透镜的引用处数与定义位置也可以反过来给地图的排序提供依据。
  典型阅读顺序：地图挑文件 → 透镜读懂文件里的每一行。地图要主动遵守透镜的克制原则：只陈述索引里能确认的事实，不含推断。
- **与 03 导航 Navigator**：地图是导航的**起点**，导航是地图的**执行**。地图上任何条目点下去都要落到导航已有的打开/定位能力上（含深链与前进后退），不另造一套跳转。
  边界也要清楚：M6.1/M6.2 是**文件/模块级**反向依赖（结构情报），导航的常驻引用面板是**符号级**引用列表（阅读工具），两者不重复实现、应互相跳转。孤立文件（M8）也是导航降噪的输入——清单里可以直接排除这些文件。
- **与 04 向导 Guide**：向导回答「按什么顺序读」，它的输入几乎全部来自地图：入口候选（M2）是路线的起点，热点榜（M3）是路线的必经点，分层（M4）与依赖图（M5）是路线的骨架，改动热力（M9）决定路线是否需要重排。
  反过来说，地图只负责「有哪些地方」，向导负责「怎么走」；地图不要越界去生成叙事型阅读路线，否则两者会变成两个相似的推荐器。
- **与 05 信使 Share**：地图是最值得带走的东西之一。无论是贴给同事，还是喂给 agent 当上下文，「这项目有几块、入口在哪、核心是哪几个文件、最近改了什么」都是最短的一份项目说明书。
  深链可以指向地图上的具体条目（如「看这个模块的反向依赖」），这要求地图的每个视图都可被 URL 表达。M10（AI 生成标记）还额外依赖信使定义的宿主通道：谁把「这段是 agent 写的」这个事实送进来，是信使要回答的问题。
- **与 06 底座 Platform**：地图是索引成果的**总展示面**，因此它的能力上限完全由底座决定——支持的语言数决定语言分布的可信度，忽略规则决定「什么算项目里的文件」，增量索引与事件推送决定热力与来源标记能否实时，内存与首屏预算决定依赖图能画多大。
  三条硬约束要提前对齐：①地图的所有数字必须注明口径（是文件还是目录、是否含测试），否则会和用户直觉冲突；②大仓必须能在不阻塞阅读的前提下出图（先出概览、图上按需展开）；③地图是只读的展示层，不允许出现任何「在地图上改代码/改结构」的动作。

## 6. 边界（明确不做）

| 不做 | 理由 |
|---|---|
| 运行时 / 构建配置级入口推断（不启动进程、不解析构建工具配置的语义） | 只读工具不执行任何东西；入口永远是「候选 + 命中依据」，不宣称唯一确定 |
| 精确依赖分析（不追动态 import、反射、依赖注入、字符串拼接出的模块路径） | 图是「import 语句级」的近似，允许存在未解析项并如实标注，不允许伪造边 |
| 完整 git 客户端（提交 / 分支 / 合并 / diff 视图） | 只借用于「读懂」的时间信号；git 一旦变成功能面就会膨胀成半个 Git 客户端 |
| 代码质量评分 / 技术债排行 / 「该重构了」的判定 | 只给客观计数与事实（有环就说有环），不做优劣裁决；给读者当判官是越界 |
| 依赖包内部结构分析 | 第三方包内部不进入地图（相关目录被忽略），外部依赖只作为聚合节点出现 |
| 跨项目 / 多仓库地图 | 地图以单个注册项目为界；跨仓关系不属于「读懂这一份代码」 |
| 用 LLM 生成项目摘要 / 目录职责描述 | M1.4 的 README 用原文截取；生成式摘要属形态级决策（见待确认问题），不在本主题默认范围内 |
| 手工整理地图（拖拽分层、手工指定入口、手工画边） | 地图全自动生成、保持可信；用户只做筛选与折叠，不做编辑，避免出现「地图与代码不一致」 |
| 在地图里做代码搜索 | 已有文件搜索 / 符号搜索 / 全项目搜索；地图只负责「看哪里值得读」，不重复检索入口 |
| 展示或跳转外部依赖包的源码 | 与产品定位一致：外部一律标注，不给假跳转 |

## 7. 演进阶段

地图的能力按「数据现成度」排序推进：先做不需要新采集、只靠聚合与呈现就能见效的，再做需要新采集或外部信息（git / 宿主）的，最后才做需要与其它主题联动的。

**阶段一：第一眼有东西看（M1 全部、M2.1/M2.2、M3.1/M3.3、M8.1）**
把首屏欢迎页换成项目概览：身份卡、语言分布、规模、入口候选、热点 Top N、孤立文件。
验收信号：打开任何项目，10 秒内能说出「约多少文件、什么语言、先读哪三个文件」，且每个结论都能一键跳到代码。
这一步不新增索引采集，全部基于已有条目表、符号表与文件树。

**阶段二：结构看得懂（M5.1/M5.2/M5.3、M6.1/M6.2、M4.1/M4.4、M11.3/M11.4）**
把 import 网络画出来，并在图上提供反向依赖；目录级聚合与逐层下钻进同一张画布。
验收信号：能回答「这个项目分几块、怎么连」，以及「我要动的这个文件，上游有谁」。
关键风险是规模——必须在大仓上默认聚合、按需展开（M5.4），否则这张图会被用户关掉。

**阶段三：骨架与噪声（M3.2/M3.4、M4.2/M4.3、M6.3/M6.4、M7 全部、M8.2、M11.1/M11.2）**
热点口径可切换、降噪规则、分层判定、传递上游、环检测、指标列。
验收信号：榜单和清单的可信度足够高，用户愿意直接按它排序阅读，而不是回头翻文件树验证。

**阶段四：时间与来源（M9 全部、M10.1/M10.3/M10.4）**
改动热力、批次视图、来源标记、阅读确认。这一步依赖「时间与来源」这两类信息的可信度决策（见待确认问题 4/5）。
验收信号：回到旧项目能立刻定位「新的那块」；一轮 agent 产出后能拿到一份清单并逐条划掉。

**阶段五：与其它主题合流（M10.2、M4.4 深化、地图快照）**
行级 agent 标记依赖宿主通道；分层视图与向导的阅读路径合流；地图快照与分享（信使）对接。
验收信号：地图能作为上下文被带走，也能作为阅读路线的起点被消费。

每个阶段的共同约束：地图只加视图、不改阅读器主流程；不阻塞首屏（索引未完成时给「部分地图 + 进度」而不是空白）；任何统计数字都要能点开看到构成（点了能列出具体文件），杜绝不可核对的汇总。

### 9.5 遗留（第二轮之后）

1. **首次概览 3 秒**（唯一明显的性能债）：引用解析结果只在内存按索引版本缓存，任何文件改动都会让它重算。下一步把「文件 → 文件」的边按 mtime 指纹落盘，冷启动与增量都能省掉重算。
2. **目录职责的覆盖率**：只截原文，所以没有 README / 文件头注释的目录只能给事实句（实测 14 个目录里多数如此）。这是刻意的取舍（§6 禁生成式摘要），若将来允许 LLM，这一格才有内容。
3. **M4.2 分层的可信度**：按「依赖方向 + 目录名惯例」判，目录名不按惯例起时只能落到「领域层」。泳道是分组展示，不是架构真值 —— 界面上已明说。
4. **大仓阈值**：文件节点 400 / 目录节点 200 是拍的初始值，还没有万级文件的真实仓库校准；泳道布局在节点很多时还没有虚拟化。
5. **快照的完整性**：视图、口径、依赖图的级别 / 展开 / 布局都已进 URL；但「拖动缩放后的视口」不还原（重开是重置视图），选中的节点也不在 URL 里。

# 主题 06：底座 Platform

[01 地图 Map](./01-map.md) · [02 透镜 Lens](./02-lens.md) · [03 导航 Navigator](./03-navigator.md) · [04 向导 Guide](./04-guide.md) · [05 信使 Share](./05-share.md) · [06 底座 Platform](./06-platform.md)

> 底座是「其它五个主题能不能真的被用上」的地基：解析能力与规模决定读懂的上限，交付与分发决定它能不能离开开发机、被同事一条命令用起来，质量与可观测决定改它时敢不敢改。

## 1. 为什么需要它（用户视角）

前五个主题回答「读懂代码需要什么功能」，底座回答「这些功能凭什么被别人用上」。目标形态是 share，而 share 的失败通常不是功能不够，是**交付不出去**：

- 同事说「这个仓库你帮我看看」，我能给的如果只有一句「先装 Node，再 npm install，再 build，再 start」，对话就结束了。用户要的是：一条命令、一个可执行文件，或者一条链接。
- AI 生成的代码量上来之后，一个仓库动辄几千到上万文件。第一次打开等 20 秒、第二次打开还要再等 20 秒（因为索引在内存里，重启就没了），用户会认为「这东西很慢」，而不是「它在建索引」。**性能不是优化项，是首次体验本身。**
- 我在自己机器上敢打开私有仓库，是因为知道代码不出本机。但如果界面上没有任何地方说过这句话，把它发给同事时对方第一反应是「这会不会把我的代码传走」——**隐私不是实现细节，是要写在脸上的承诺。**
- 解析失败时（`obj.method()` 跳不动、GBK 文件打开是乱码、1MB 以上的大文件搜不到符号），用户会默认「工具坏了」。底座要做的是把「解析不了」变成一句人话解释，让用户知道边界在哪，而不是默默不响应。
- 一个能改得动的产品需要测试、lint、日志、基准。现在后端有 32 个用例，前端和 UI 回归没有常驻入口，改一行 UI 只能靠人肉点——这会直接决定 Phase 1/V1 之后还敢不敢动代码。

底座不直接产生「我懂了」的瞬间，但它决定了那些瞬间能不能发生在别人身上。可以把 25 项能力收敛成三条主线：

- **能读懂**（P1–P3、P8–P12）：语言、精度、编码、忽略规则、大文件、monorepo，决定「这个仓库我能不能读」。
- **供得起**（P4–P7、P23）：持久化、并行、增量、对账、基准，决定「第一次要等多久、长期开着准不准」。
- **交得出**（P13–P17、P18–P22、P24–P25）：分发、启动、引导、隐私、测试、lint、日志、偏好、无障碍，决定「别人能不能用上、我敢不敢继续改」。

三条主线里，「交得出」是当前短板最集中的一段，「能读懂」是差异化最容易被感知的一段。

## 3. 关键交互形态

### 3.1 一键启动与分发：用户视角只有「一条路径」

分发形态未定（见第 8 节），所以这里画的是三条候选路径共用的体验骨架——无论选哪条，用户看到的都应该是「一次动作 → 浏览器自动打开 → 能填路径」。

```
路径 A：npx（面向装了 Node 的人）
  $ npx web-code-reader
  ┌────────────────────────────────────────────────────────┐
  │ web-code-reader                                        │
  │ 端口 8787 已被占用，改用 8788                          │
  │ 已在 http://127.0.0.1:8788 打开（复用已有实例？否）    │
  │ 打开本机目录以开始阅读（只读，不会上传任何文件）        │
  └────────────────────────────────────────────────────────┘
         │ 自动唤起浏览器
         ▼
  [ 打开本机目录 ]  ← 输入 D:/code/my-project

路径 B：单文件 exe（面向没装 Node 的人）
  双击 [web-code-reader.exe]
         │
         ├─ 首次运行：后台解包 + 建数据目录（一次性，几秒）
         ├─ 起服务（自动选端口）
         ├─ 打开默认浏览器 → 空状态引导（见 3.2）
         └─ 托盘/控制台可关闭；重复双击 → 聚焦已有实例，不再起第二个

路径 C：Docker（面向团队/内网）
  $ docker run --rm -p 8787:8787 -v D:/code:/work:ro web-code-reader
  ┌────────────────────────────────────────────────────────┐
  │ 只读挂载：容器对挂载目录无写权限                        │
  │ 提示：请用 /work/my-project 作为项目路径打开             │
  └────────────────────────────────────────────────────────┘
```

三个共同要求：
1. **不因为端口占用而失败**——自动往后找可用端口，并把实际地址告诉用户。
2. **不重复起进程**——已在运行就给出现有地址（或直接聚焦），避免用户面对多个「哪个才是我的」。
3. **启动即完成一次隐私声明**——第一屏就说清楚只读、不上传、不出本机。

### 3.2 首次使用引导：从空白页到「我知道下一步」

现在打开页面只有一句提示文案（`frontend/src/App.tsx:197`）。目标形态把这一步做成三步，且**第二步是这套产品的核心承诺**：

```
┌──────────────────────────────────────────────────────────────────┐
│  web-code-reader                          只读 · 不上传 · 不出本机│  ← 常驻角标（P17）
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│            读懂一份代码，从「打开本机目录」开始                   │
│                                                                  │
│   ① 粘贴一个本机绝对路径                                          │
│      [ D:/code/my-project                    ]  [ 打开 ]          │
│      提示：目录保持原样，本工具不会写入、不会修改任何文件          │
│                                                                  │
│   ② 也可以直接打开最近的项目                                       │
│      · xchen            3 分钟前   · my-service      昨天         │
│                                                                  │
│   ③ 索引进度（首次打开大仓库时）                                   │
│      正在建立索引 ██████████░░░░░░  412 / 1830 文件               │
│      可先读文件正文；符号跳转在完成前可能不完整                    │
│                                                                  │
│   索引完成后：                                                    │
│      1830 文件 · 1795 已建符号索引 · 35 未索引（原因见下）          │  ← P9 报告入口
│      为什么没索引上？ 35 个（大文件 30 / 二进制 2 / 解析失败 3）   │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

要点：
- **引导不是教程，是让用户 5 秒内做出第一次成功操作**：填路径 → 看到文件树。
- 索引进度必须给出「现在能不能用」的判断，而不是只给百分比。
- 「未索引原因」是 P9 的界面出口：它把「工具坏了」翻译成「这 35 个文件为什么没进来」。

### 3.3 隐私承诺在界面上怎么表达：一处常驻 + 一处可追证

```
状态条（常驻，不打扰）
┌──────────────────────────────────────────────────────────────┐
│  [项目 my-project]      只读 · 不上传 · 代码不出本机   ● 已索引│
└──────────────────────────────────────────────────────────────┘
                                  │ 点击
                                  ▼
帮助面板（可追证的承诺，不是口号）
┌──────────────────────────────────────────────────────────────┐
│  隐私与数据                                                   │
│                                                              │
│  读什么：你打开的本机目录里的源码文件（按忽略规则筛选）        │
│  写什么：不写你的代码目录；只在本工具自己的数据目录里存         │
│          「项目列表」与（若启用）索引缓存                      │
│  传什么：不发起任何外部网络请求；没有账号、没有遥测、没有上报   │
│  谁在用：服务只监听 127.0.0.1，同一台机器上的进程才能访问      │
│                                                              │
│  可自证：                                                     │
│    · 删除任何项目只移除列表项，不删磁盘文件                    │
│    · CORS 默认放开仅用于宿主内嵌，可设为具体来源收紧           │
│    · 关闭监听：READER_WATCH=0                                 │
└──────────────────────────────────────────────────────────────┘
```

原则：
- 承诺必须**可核对**（说清写哪里、监听哪里、能不能关），否则和口号没有区别。
- 与 P14/Docker 形态配套：只读挂载是「物理上写不了」的更强表达。
- 若未来引入联网能力（如 LLM 解释），必须在这一面板里显式增量声明，不能悄悄改口径。

## 4. 与其它五个主题的关系

底座是横切面：它自己不产出功能，但没有它，五个主题的功能都停在「我机器上能跑」。

| 主题 | 底座提供什么 | 底座不达标时的后果 |
|---|---|---|
| 01 地图 Map | 全量扫描与符号/引用统计（热点、反向依赖、语言分布全建立在索引上）；P4 持久化决定地图页能不能秒开 | 每次看地图都要等全量索引；万级文件仓库直接不可用 |
| 02 透镜 Lens | P2/P3 决定 Hover、签名、类型、文档能显示多少；P12 决定正文不乱码；P24 决定对比度与字号是否可调 | 悬停只能显示已有解析结果；GBK 文件整篇不可信 |
| 03 导航 Navigator | P2 决定跳转成功率；P9 把「跳不了」解释成人话；P6+P7 决定增量更新后跳转还准不准 | 跳转失败无解释，用户无法判断是工具问题还是代码问题 |
| 04 向导 Guide | P13/P16 是向导的前置：先能一键打开，才轮到「从哪开始读」；P5/P23 决定大仓库的阅读路径能否快速算出来 | 还没打开项目，向导无从谈起 |
| 05 信使 Share | **底座直接决定 share 的成立**：P14 决定能不能发给别人、P17 决定别人敢不敢用、P20/P21 决定改得快不快、P22 决定出问题能不能远程定位 | share 退化为「截图 + 口头描述」 |

一句话概括依赖方向：**底座决定下限，其它主题决定上限。** 底座的每一项缺口都会被上层主题放大成「功能做了但用不上」——地图页做得再好，索引要等 20 秒也没人看；深链分享做得再好，对方没有 Node 也点不开。

反向依赖（这五个主题对底座提的要求）：
- 地图要「热点清单」，等于要求底座能一次性输出稳定统计（最好持久化，避免每次重算）。
- 向导要「先看 A 再看 B」，等于要求索引里带调用/依赖关系，且关系要能增量维护。
- 信使要「给 agent 用」，等于要求后端接口稳定（P18/P20 是接口稳定的前提）。

## 5. 现状证据（只列事实）

索引与规模

- 忽略规则是硬编码：目录黑名单与文件模式表见 `backend/src/indexer/store.ts:19-24` 与 `:26-33`；未读取任何 `.gitignore` / `.wcrignore`（全仓无相关解析代码）。
- 大小阈值：`MAX_INDEX_BYTES = 1_000_000`（`backend/src/indexer/store.ts:36`）、`MAX_VIEW_BYTES = 5_000_000`（`backend/src/indexer/store.ts:38`）；超过 1MB 的文件在扫描阶段就被排除出索引目标（`backend/src/indexer/store.ts:157`），在 `indexOne` 里再次跳过（`:200`）。
- 全量索引为串行 for 循环，逐个 `await this.indexOne(...)`（`backend/src/indexer/store.ts:161-169`），入口为 `reindexAll`（`:146`）。
- 源码一律按 UTF-8 读取：`source = buf.toString('utf8')`（`backend/src/indexer/store.ts:206`），无编码探测。
- 文件读取失败在 `indexOne` 里静默 `return`（`backend/src/indexer/store.ts:209-211`），不记录该文件为何未入索引。
- 未索引文件在文本搜索时按需读盘并缓存：`ensureText`（`backend/src/indexer/store.ts:389`）、`cacheText`（`:418`），缓存为 Map（LRU 上限 2000 的说法见 `FR/FR-0002-fr.md:379-380`）。

## 6. 边界（明确不做）

| 不做 | 理由 |
|---|---|
| 编译 / 运行 / 调试 / 重构 / 类型检查 | 只读定位是差异化；做了就变成半个 IDE，永远打不过 VS Code |
| 自研类型推断引擎 | 类型推断属于 LSP 领域。要么不提升精度，要么接现成的，不自己造（P3 的决策属「接不接」而非「写不写」） |
| 索引 / 分析依赖包内部（node_modules、site-packages 等） | 边界清晰：外部一律标 `external` 不跳转；索引外部包会让规模与耗时失控 |
| 账号 / 云端托管 / 多人协作服务 | 本机工具，隐私即卖点；P17 的承诺与云托管天然冲突 |
| 遥测、崩溃上报、自动更新检查（默认） | 任何出网行为都会削弱「代码不出本机」的可信度；若要做必须显式开关 + 界面声明 |
| 写回源码（批注、格式化、保存） | 与只读承诺冲突；批注类需求归入 04 向导的本地记忆，不落源码 |
| 通用 IDE 服务器 / 完整 LSP 代理 | 目标不是给编辑器做后端，只借用 LSP 能力提升解析精度 |
| 为「万级文件」做分布式 / 多机索引 | 单机本地工具，规模问题用并行 + 持久化 + 降级策略解决，不上集群 |

## 7. 演进阶段

阶段划分以「能不能交付出去」为主线，与 V3（带得走）对齐；每阶段给可验证的完成标志。

| 阶段 | 主题 | 覆盖能力 | 完成标志（可验证） |
|---|---|---|---|
| 阶段 0：可信（现状加固） | 让现状可核对、可回归 | P18 保持、P20 补齐、P21、P22 起步 | UI 回归脚本进入正式测试目录并能在一条命令下跑；lint 接入并零 error；跳转失败 / 索引异常有日志可查 |
| 阶段 1：可解释 | 把「跳不动」变成人话 | P2、P9、P12、P8 | 未索引文件有可查原因清单；GBK 文件中文注释不乱码；忽略规则可由配置文件调整并能看到生效结果 |
| 阶段 2：能交付 | 一条命令 / 一个产物给别人用 | P13、P14、P15、P16、P17 | 无 Node 环境的一台机器上，双击或一条命令即可打开页面并完成「填路径 → 看到文件树」；端口占用自动让位；重复启动不产生第二个实例；界面常驻隐私承诺 |
| 阶段 3：撑住规模 | 大仓库也能秒开、长期开着也准 | P4、P5、P7、P11、P23 | 冷启动二次打开不等全量索引；万级文件仓库首开时间有预算且被基准守护；索引与磁盘定期对账，监听漏事件可自愈；超 1MB 文件在大纲/符号搜索里可见 |
| 阶段 4：撑住团队协作 | 多语言、可扩展、可长期维护 | P1 扩展、P10、P19、P24、P25 | 至少新增一种语言只需一个独立模块且不触碰核心；monorepo 跨包跳转不再落 external；前端单测 + UI 回归进 CI；主题/字号可切换并持久化；键盘可完成主流程，文案可切换语言 |
| 阶段 5：精度跃迁（取决于决策） | 接现成 LSP 或维持无类型推断 | P3 | 若引入：未解析比例显著下降且跳转错误率不上升，界面对「来自 LSP」与「来自索引」的结果有区分；若不引入：`unresolved` 一律给缺失原因说明 |

阶段 0/1 不依赖用户决策即可推进；阶段 2 必须先在「分发形态」上拍板（第 8 节第 2 条）；阶段 5 完全取决于第 1 条。

## 8. 待确认问题

1. **是否引入类型推断 / 接入现成 LSP？** 现状 15.8% 的引用因缺少类型信息无法解析，典型是 `self.session.get()`。请选：A. 不引入，维持「宁可不着色也不标错」，只在 UI 上把 `unresolved` 解释清楚；B. 接入现成的语言服务器（需要为每种语言配一个外部进程，安装与启动复杂度上升）；C. 只对 Python / TypeScript 两种主力语言引入，其它语言维持现状。
2. **分发形态选哪种？** 请选一个主形态（可多选但需要排优先级）：A. 源码启动（`npm start`，用户需装 Node）；B. npx 一键（用户需装 Node，无构建步骤）；C. 单文件 exe（用户无需装 Node，我这边要维护打包）；D. Docker 镜像（面向团队/内网，挂载只读目录）。这一条同时决定 P13 / P14 / P15 的验收口径。

# 网页版代码阅读器完整方案

## 一、产品定位

**一句话**：一个跑在浏览器里的代码阅读器，让用户快速读懂 AI 生成的代码。

**核心场景**：
- Agent 生成代码后，用户想快速理解结构
- 用户问“这个函数在哪被调用”，点击就能看
- 用户想找“所有处理用户的代码”，搜一下就出来

**明确不做**：编译、运行、调试、类型检查、重构、依赖包内部符号分析。


## 二、技术选型（最终决策）

| 层 | 选型 | 理由 |
|---|---|---|
| **后端语言** | **TypeScript** | MCP官方SDK中TypeScript是Tier 1；tree-sitter有Node.js和WASM双绑定；与前端共享类型 |
| **后端框架** | Hono / Fastify | 轻量、TypeScript原生 |
| **代码解析** | `tree-sitter` (Node绑定) | Node.js绑定成熟，支持定义/引用提取 |
| **前端框架** | React / Vue | 任意选择 |
| **代码编辑器** | **Monaco Editor** | VS Code同款，内置DefinitionProvider/ReferenceProvider接口 |
| **构建工具** | Vite + `vite-plugin-monaco-editor-esm` | 简化Monaco的ESM加载 |

### 4.3 符号解析（核心逻辑）

**就近原则**：从引用位置所在的作用域开始，沿作用域链向上查找，找到最近的同名定义。

```typescript
function resolveSymbol(file: string, node: Node): SymbolId | null {
  let scope = findScopeAt(file, node.startPosition);
  
  while (scope) {
    // 1. 查本地定义
    if (scope.definitions.has(node.text)) {
      return scope.definitions.get(node.text);
    }
    // 2. 查导入
    if (scope.imports.has(node.text)) {
      return resolveImport(scope.imports.get(node.text));
    }
    scope = scope.parent ? project.scopes.get(scope.parent) : null;
  }
  return null;  // 未解析（可能是内置符号或外部依赖）
}
```

**导入解析**：区分内部模块和外部依赖。内部模块转成文件路径，在目标文件的作用域中查找；外部依赖标记`external`，不跳转。

```typescript
import * as monaco from 'monaco-editor';

// 注册跳转定义
monaco.languages.registerDefinitionProvider('python', {
  async provideDefinition(model, position) {
    const res = await fetch(`/api/projects/${projectId}/goto-definition`, {
      method: 'POST',
      body: JSON.stringify({
        file: model.uri.path,
        line: position.lineNumber,
        col: position.column,

    const { locations } = await res.json();
    return locations.map(loc => ({
      uri: monaco.Uri.file(loc.file),
      range: new monaco.Range(
        loc.range.start.line, loc.range.start.col,
        loc.range.end.line, loc.range.end.col

    }));
  },
});
```

## 七、关于未来嵌入Code Agent

你之前提到未来想嵌入Claude等Code Agent。TypeScript是正确选择：

- **MCP官方SDK**中，TypeScript属于**Tier 1**（功能最完整、维护承诺最高）
- 如果未来需要让Agent也能用你的索引能力，**在同一个后端加一层MCP Server**即可，不影响网页阅读器
- 两者共享同一个索引引擎，只是暴露方式不同


## 八、关键决策总结

1. **后端用TypeScript**：MCP生态第一梯队，tree-sitter绑定成熟
2. **索引跑后端，前端只查询**：性能不受限
3. **Monaco的Provider接口**：F12/Shift+F12/大纲零成本实现
4. **只读为主**：不做编辑，专注阅读体验
5. **项目导入后全量索引**：简单可靠
6. **不做依赖分析**：保持范围约束


## 九、几个坑

1. **位置坐标统一**：前后端都用1-based行列，UTF-16（Monaco默认）
2. **Monaco多model管理**：切换文件时注意dispose，否则内存泄漏
3. **tree-sitter版本匹配**：语言语法文件版本要和核心库匹配
4. **大文件保护**：超过1MB的文件跳过索引，只做文本搜索
5. **临时目录清理**：定时任务清理过期项目，防止磁盘满
6. **路径安全**：API校验路径在项目根内，防路径穿越


**总结**：这是一个定位清晰的轻量产品——网页版代码阅读器，2~3周可出可用版本，后端TypeScript，前端React+Monaco，为未来嵌入Code Agent留好了扩展路径。

## 结果

### 一、结论

方案里的 Phase 1 / 2 / 3 全部落地，是一个可直接跑起来的可用版本（不是脚手架）：

- 后端 TypeScript + Hono + `tree-sitter` Node 绑定：目录扫描 → 解析 → 作用域/定义/引用索引 → 符号解析 → HTTP API。
- 前端 React + Monaco：文件树、大纲、搜索面板、F12/Shift+F12/Ctrl+Shift+O 全部通过 Monaco 的
  Definition / Reference / DocumentSymbol Provider 实现，没有自造 UI。
- 语言覆盖：Python、TypeScript、TSX、JavaScript、JSX、Go、Java（首版口径由你确认）。
- 项目以「本机目录」为单位管理（按需求末尾备注），并给 xchen 项目列表预留了接入接口（见第五节）。

真实项目实测（本机 `D:/01_code/02_work_code/xchen/xchen`，191 个 Python 文件）：

- 全量索引 4.1 秒，192 个文件进文件树。
- 抽样 12722 处引用做跳转：精确解析 53.3%、判为外部依赖 30.9%、未解析 15.8%（未解析基本都是
  `obj.method()` 这类需要类型推断的场景——本方案明确不做类型推断）。
- 浏览器端 12 项 UI 回归全绿（详见第四节）。

### 三、与方案不同的决定（动手前已口头对齐，这里补记）

1. **项目接入 = 注册本机目录，不做 zip 上传**。按需求末尾备注「以项目(目录)来管理源码」，
   API 从 `POST /api/projects`（上传 zip）改为 `POST /api/projects { root }` 直接索引本机目录。
   同一目录永远得到同一个 id（`sha1(root)` 前 12 位），宿主可直接推导。
   好处是不复制源码、文件变更天然实时；代价是服务必须与源码在同一台机器上（本地/内网工具，成立）。
2. **没用 `vite-plugin-monaco-editor-esm`**：该插件不兼容 Vite 6 + monaco-editor 0.52，
   改用官方推荐的 worker 显式注册（`monaco-setup.ts` 顶部），构建已验证通过。
3. **实时更新用 SSE 而不是 WebSocket**：这里只有服务端单向推事件，SSE 更简单且能自动重连。
4. **`find-references` 前端表现为 Monaco 的 Peek 视图**（Shift+F12 弹出 "References (16)"），
   与 VS Code 一致，没有另做结果面板。
5. **`npm install` 需要 legacy-peer-deps**：`tree-sitter-typescript@0.23.2` / `tree-sitter-java@0.23.5`
   的 peerOptional 仍写着 `tree-sitter@^0.21`，实测与 `^0.25` 内核兼容。已固化在
   `backend/.npmrc`，正常 `npm install` 即可。

### 六、遗留问题 / 后续建议

1. **没有类型推断**（有意为之）：`obj.method()` 中 `obj` 是局部变量时无法确定类型。
   若要覆盖，需要额外的类型推断或引入真正的 LSP，属于量级变化，建议单独立项。
   当前忠实返回 `external`（内置/外部依赖，不跳转）或 `unresolved`（不确定），不做错误跳转。
2. **索引不持久化**：进程重启后首次访问重建索引（191 文件约 4 秒；万级文件会明显变慢）。
   方案 §5「持久化索引」尚未做。
3. **CommonJS `require()` 不解析**（ESM `import` 正常）。
4. **大文件只做文本搜索**：正确但有代价——全项目搜索会读盘所有未索引文本文件并缓存
   （LRU 上限 2000 个），超大仓库首次搜索会慢。如需可加索引期文本倒排。
5. **前端没有常驻自动化测试**：UI 回归脚本目前在 `tmp/uitest/check.mjs`（临时目录，可随时清）。
   若要长期守护，建议把它移进正式测试目录并加进 CI。
6. **Go 模块 path 依赖 `go.mod`**：`vendor`/多 module 仓库里跨 module 跳转可能落到 `external`。
7. **`F12` 在部分浏览器被 DevTools 占用**：已提供等价路径（Ctrl+Click、右键菜单、Ctrl+F12），
   帮助弹窗与 README 都有说明。

### 关键设计决定

1. **只提亮「模块级 / 类级」定义**（函数、类、方法、属性、常量），局部变量与参数降一档。
   若局部变量也按最亮档渲染，文件里密度最高的名字会整体发白，反而淹没「哪里是外部依赖」这个信号。
2. **解析不出的成员访问不着色**：`obj.method()` 里的 `method` 需要类型推断才能确定归属，
   保持编辑器语法色。宁可不着色，也不标错。
3. **`self` / `this` 这类语法成分不着色**（它们既不是「本项目符号」也不是「依赖」）。
4. **三档颜色做成 CSS 变量**，集中在 `frontend/src/styles.css` 顶部，方便随时调对比。
5. **不新开语法解析**：着色数据由 `highlightSpans()` 复用 `resolveRef` 的解析结果，
   并带索引版本缓存（`indexVersion` 变化即失效），单文件开销与 goto-definition 同量级。
6. **覆盖索引空窗期**：首次打开大项目时索引可能还没跑完（此时没有任何着色），
   前端在收到 `index-ready` SSE 事件后自动重拉着色，无需用户刷新。

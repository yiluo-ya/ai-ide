# FR-0010 · 模型 API 类型选择 + 测试连接

## 一、为什么做（用户视角）

顶栏「模型」里配的是内置 code-agent 用的 provider。原来只认一种形状 —— OpenAI 兼容的
`/chat/completions`：用 Claude（Messages API）、GPT-5 系（Responses）、Gemini 的人根本配不进来。

而且配错了（key 错、模型 id 写错、地址少一段）当场看不出来，要等到真正对话时才抛一句
HTTP 4xx，人得自己猜是哪一步错。→ 要能**选 API 类型**，并且**先测通再保存**。

## 二、已拍板（2026-10-13，用户答表）

1. 支持四种 API 类型，且都**真按各自协议发请求**（不是只存一个字符串）：
   OpenAI 兼容 `/chat/completions`、Anthropic Messages `/v1/messages`、
   OpenAI Responses `/responses`、Google Gemini `:generateContent`
2. 测试粒度：「填完参数后，点击测试，看能不能连通，测试不通过，不保存」
3. 测试对象是**表单里还没保存的值**（先测试，再保存）
4. baseUrl 预设：要，选类型 / 点预设就带出常见地址

## 三、默认（我的判断，不同意就直说）

- `apiType` 是 provider 级字段；旧配置没有这一项时一律按 openai 兼容算（不写坏老文件）
- 预设做成「快速填充」一排 chips（OpenAI / DeepSeek / Moonshot / Zhipu GLM / Qwen / Anthropic /
  Gemini），点一下同时填类型与 base URL，仍可手改；**切类型时只覆盖「还是预设值」的 baseUrl**，
  用户手填的地址不动
- 测试发**非流式**最小请求（输出上限 16 token），逐个模型给一条结果：✓/✗ + 耗时 +
  回复摘要（失败时给对方返回的错误原文，如 `invalid api key`）
- 编辑已保存的 provider 时表单不回填明文 key；此时点测试，服务端**回退用已存的那把 key**

## 六、明确不做

- 从 `/models` 拉模型清单（用户没要）；模型 id 仍手填
- 流式「测试」（测试只要通不通）、用量/费用统计
- 自定义协议的插件化（加协议仍是改代码 + 一行 case）
- 改 pi / OpenHands 后端的凭证方式（pi 有自己的 `auth.json`）
- 把 baseUrl 预设做成完整的「服务商目录」（只给一排常用 chips）

### 与本文的偏差

1. 名称口径：`apiType` 的取值用 `openai-responses` 而不是 `responses`（避免与「后端类型」混淆）；
   界面上仍显示「OpenAI Responses」。
2. `llm-util.ts` 是实施时临时拆出来的：一开始把共享类型与 SSE 工具放在 `llm.ts`，就出现
   `llm.ts → anthropic.ts → llm.ts` 的循环 import，索性单独成文件（协议实现只依赖它）。
3. Anthropic 的 `max_tokens` 必填，默认给 8192；Gemini 的 `maxOutputTokens` 同理。
4. 三套新协议**没有真机 key 可验**（本机只有 OpenAI 兼容的 key）：形状与解析由单测 + 本地假端点
   断言，真实服务端的兼容性待有 key 时复测（尤其 Gemini 的 schema 子集限制）。
